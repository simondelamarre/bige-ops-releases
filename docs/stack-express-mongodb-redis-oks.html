bige-ops Gratuit

Express + MongoDB + Redis + BullMQ sur OKS

Une API Express, MongoDB pour la souplesse du document, Redis et BullMQ pour les jobs : un classique des startups Node. Sur OKS, chaque brique devient un Deployment, l’API et ses workers montent en charge avec l’HPA, et Outscale opère le control plane.

En bref. Topologie oks : control plane cp.mono.master, nodepool de 3 nœuds tinav6.c4r8p2, Kubernetes 1.34. Deployments api, web, worker BullMQ, MongoDB et Redis ; backups MongoDB vers OOS. Estimation bige-ops : 457,65 € HT par mois, plus les LBU créés par les Services exposés.

Architecture sur Outscale

  • Cluster OKS en eu-west-2 : Outscale opère le control plane ; bige-ops part sur cp.mono.master et Kubernetes 1.34, et génère cluster, nodepool et manifests (oks-cli puis kubectl apply).
  • Nodepool de 3 nœuds tinav6.c4r8p2 : 12 vCPU et 24 GiB pour les pods.
  • api (Express, 2 réplicas par défaut, HPA sur le CPU possible), web (2 réplicas), worker BullMQ (1 réplica, à monter selon la file).
  • MongoDB 8.0 et Redis 8 en pods, Services internes. Les pods de bases démarrent sur emptyDir : leurs données vivent avec le pod, et le filet est le backup vers OOS, activé ici.

OKS est disponible en eu-west-2 et en cloudgouv-eu-west-1 (SecNumCloud) et s’active sur demande auprès du support Outscale ; la simulation et l’estimation n’en dépendent pas. Détail : OKS & pods.

LBU des Services exposés. api et web sont des Services LoadBalancer : OKS crée un LBU pour chacun, à 21,90 € HT par mois l’unité au même catalogue, soit 43,80 € de plus : 501,45 € HT par mois au total.

Variante production. Le même cluster avec un control plane haute disponibilité cp.3.masters.small (3 masters, jusqu’à 50 nœuds) : 523,35 € HT par mois estimés, 567,15 € avec les deux LBU. C’est la recommandation d’Outscale pour la production.

Le projet utilisé, à reproduire chez toi :

bige-ops init -n stack-express-mongodb-redis-oks
bige-ops add layout custom --name app --runtime nodejs --web same --worker \
  --db mongodb --db redis --topology oks --lbu
# puis project.yaml ajusté comme ci-dessous
bige-ops validate
bige-ops estimate --json
name: stack-express-mongodb-redis-oks
region: eu-west-2
components:
- type: stack
  name: app
  topology: oks
  services: [api, web, worker, mongodb, redis]
  images: {mongodb: 'mongo:8.0', redis: 'redis:8-alpine'}
  service_config:
    mongodb:
      backup: {enabled: true, oos_bucket: express-app-backups}
- {type: oos_bucket, name: express-app-backups, bucket: express-app-backups, size: 50, purpose: backups}

MongoDB. Le tag mongo:8 par défaut de bige-ops suit la dernière 8.x ; la simulation épingle mongo:8.0, la branche de référence de la génération 8. Côté durcissement : l’authentification activée dès l’initialisation (utilisateur root et utilisateur applicatif distincts), une écoute limitée au réseau privé, et la checklist sécurité MongoDB.

Redis. La simulation garde redis:8-alpine, le tag par défaut de bige-ops : il suit la dernière Redis 8. Épingle la mineure (par exemple 8.10) si tu veux un build strictement reproductible. Côté durcissement : un mot de passe ou des ACL, le protected mode actif, aucune exposition publique, et les commandes d’administration réservées à un utilisateur dédié (sécurité Redis).

Côté Node, Mongoose (CVE Mongoose) et BullMQ se branchent sur les Services internes mongodb:27017 et redis:6379. Les réplicas de pods ne forment pas un replica set MongoDB : voir bases complexes.

Le backup est activé dans la simulation (backup.enabled + bucket OOS) : bige-ops crée le bucket, protégé contre la destruction, et prépare backup.sh (bucket, endpoint, planning) où tu branches le dump. Sans backup, Visual, preflight et plan te le signalent. Détail : OOS & backups.

Exposition : ce qui est ouvert, et à qui

  • Entrées publiques : l’API Express (api) et le front (web). Chacune est un Service LoadBalancer, donc un LBU Outscale ; le HTTPS se branche avec expose.tls.server_certificate_id (ORN d’un certificat EIM) et le LBU termine le TLS, sans Ingress ni cert-manager à maintenir.
  • Bases et brokers : Services internes (ClusterIP), joignables seulement depuis le cluster. Jamais de type: LoadBalancer ni de NodePort vers une base.
  • API Kubernetes : à l’apply, l’accès admin du cluster est restreint à ton IP publique (/32) ou au CIDR de OKS_ADMIN_CIDR.
  • Nœuds : workers jetables gérés par OKS ; ne fonde aucune règle sur leurs IP.

Détail : OKS & pods, réseau · ouvrir ou non, load balancers dans OKS.

Vulnérabilités : ce que bige-ops vérifie

Avec ta clé API OpenCVE (Settings), l’onglet Vulnérabilités lit ta simulation : chaque composant reconnu, image Docker ou package, est rapproché de sa fiche fournisseur / produit, à raison d’une requête par produit. Les CVE remontées sont classées par risque :

  • Sévérité : score CVSS (critique dès 9, haute dès 7, moyenne dès 4), relevée au moins à « haute » quand la faille figure au catalogue KEV des vulnérabilités exploitées.
  • Exposition dans ta simulation : un composant joignable depuis Internet ou derrière le LBU garde sa sévérité ; un composant en subnet privé descend d’un cran, sauf s’il est KEV.
  • Départage : à risque égal, KEV d’abord, puis CVSS, puis EPSS. Un filtre « important » ne garde que KEV ou CVSS ≥ 7.

Le rapprochement se fait au niveau du produit : tu recoupes ensuite avec la version que tu as épinglée. Une image en latest ressort en plus comme « version non épinglée ». Le résultat est mis en cache dans la simulation et se rafraîchit à la demande.

Mode direct, sans clé : routes Express (et Fastify, Koa, Hono si tu les mélanges), signaux d’authentification, failles de code, dépendances npm (Express, Mongoose, BullMQ…) rapprochées d’OSV. Détail : Node.js sur Outscale.

bige-ops advanced va plus loin avec ta propre clé LLM : un agent d’audit reprend les pistes pré-mâchées (routes ouvertes, motifs à risque, pièges connus du framework), confirme les vraies failles, écarte les faux positifs et classe chaque trouvaille par CWE, avec sa priorité (P0 à P3), son exposition et une issue GitHub proposée. Les appels partent de ton poste ; ni apply, ni lecture des secrets. Voir l’assistant IA.

Ce que bige-ops vérifie avant le deploy

  • bige-ops validate : structure du projet, services custom (une image est requise pour un pod), HTTPS par expose.tls.server_certificate_id (ORN EIM).
  • bige-ops preflight : clés Outscale présentes, OMI résolue, stack déclarée, IP des hôtes après l’apply, Dockerfile trouvé, secrets de build et d’exécution présents dans le coffre, jeton GitHub pour les dépôts privés, et alerte si une base n’a pas de backup vers OOS. Une erreur bloque le deploy.
  • bige-ops plan : le plan Terraform et les specs OKS avant tout apply, avec les risques de perte de données signalés ; les buckets OOS sont protégés contre la destruction.
  • Vulnérabilités : composants de la stack confrontés à OpenCVE et classés par exposition, tags latest signalés, dépôts analysés en mode direct.

OpenCVE, le référentiel CVE de bige-ops

Pour savoir quelles vulnérabilités touchent les briques de ta stack, bige-ops s’appuie sur OpenCVE. OpenCVE agrège les CVE publiées (NVD, MITRE, catalogue KEV de la CISA…), les enrichit avec les scores CVSS et EPSS et les range par fournisseur et par produit, consultables dans son explorateur. Le projet est open source : son code, ses issues et les contributions de sa communauté vivent sur GitHub, et il s’installe aussi chez toi. Merci à ses mainteneurs et à tous ceux qui font vivre ce référentiel : c’est grâce à eux que chaque composant de ta simulation a sa fiche CVE à jour.
