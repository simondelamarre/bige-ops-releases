Bases de données

Postgres, MongoDB, Redis (et bases custom) : tu choisis où elles tournent (même VM, VM dédiée, ou pods OKS), tu règles réplicas et volumes dans le formulaire, et le setup se met à jour tout de suite. Les sauvegardes se règlent sur la base, et son panneau Données fait le dump, la restauration et la migration ; le tuning fin reste le tien. Pour MongoDB 8, Postgres pour le RAG, Cassandra ou Elasticsearch : bases complexes.

Schéma mental. Trois placements possibles pour la data. Le formulaire ne pose pas dix questions : il écrit la simulation, puis generate produit la configuration.

1 · Coloc ou VM dédiée

En mono-VM (code single-vm), la base est colocalisée avec l’app : un seul blast radius, une estimation basse, idéal pour projeter. Pour isoler la data, passe à une VM dédiée (rôle data en multi-VM) : sizing propre, disque racine io1 par défaut pour Postgres, MongoDB et les autres bases persistantes, et un volume attaché pour la persistance. Le canvas lie le service à sa VM et à son volume ; Save réécrit project.yaml sans questionnaire.

En multi-VM, une petite base peut aussi tourner sur la VM privée d’une autre base : champ Machine de l’inspecteur, ou service_config.redis.colocate_with: weaviate. Une VM de moins dans l’estimation ; la VM hôte garde sa taille, ses groupes de sécurité s’additionnent, deploy et backups suivent. La validation refuse deux bases sur le même port (MySQL + MariaDB) ou une VM hôte trop petite pour la mémoire déclarée. Déplacer une base déjà déployée ne copie pas ses données.

2 · Sur OKS : StatefulSet et volume persistant

En topologie oks, chaque base est un StatefulSet avec son volume persistant (PVC, 10 GiB par défaut, dans la classe de stockage par défaut du cluster ; storage_gb et storage_class se règlent par base). Pour MongoDB, le champ réplicas (service_config.mongodb.replicas, 1, 3 ou 5) pose un replica set. Les autres bases restent à un pod : leur réplication se configure dans le moteur, ou avec un opérateur. Le backup vers OOS, un CronJob par base, reste le filet. Voir aussi OKS & pods. 

service_config:
  postgres:
    replicas: 1
  mongodb:
    replicas: 1

3 · Stockage bloc et sauvegardes objet

Sur une VM, la persistance passe par le volume BSU attaché à la VM data, et les snapshots de volume sont le premier filet. Pour les dumps applicatifs, on branche OOS (l’Object Storage Outscale, compatible S3) : bucket dédié, lien backup base → OOS dans Visual, script backup.sh préparé après generate et installé en tâche planifiée par le deploy (CronJob sur OKS). Le panneau Données d’une base sert au dump à la demande, à la restauration et à la migration depuis une autre base. Détail : OOS & backups.

Pas de backup, pas de filet. À la destruction, bige-ops affiche les risques selon le setup : en mono-VM, app et bases partagent le même disque, et le filet, c’est le dump vers OOS. En multi-VM ou sur OKS, détruire une VM data ou des pods efface les données vivantes ; les buckets OOS, eux, restent protégés.

Presets par type

Chaque type amène une image et des champs utiles dans l’inspector. Postgres : volume data, attache à une VM ou à un pod. MongoDB et Redis : même logique (coloc, dédiée ou OKS), avec le replica set en plus pour MongoDB. Custom : image + port + les mêmes leviers de sizing et de réplicas. Un champ changé, et le setup est à jour.

TypeDémarrage typiqueLevier formulaire
Postgres Image + volume VM ou pod, GiB
MongoDB Coloc ou pod Placement, replica set (1, 3 ou 5)
Redis Cache léger Coloc app ou OKS
Custom Image + port Mêmes leviers
