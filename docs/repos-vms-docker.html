01 / CONNECTER

Relier le dépôt GitHub.

Associer le dépôt à l’application, à l’API ou au worker de la stack. Définir le chemin du service et son contexte de build : bige-ops sait quel code préparer pour cette cible.

Dépôt GitHub→Service relié

Code applicatif et configuration d’infrastructure gardent leurs dépôts respectifs.

02 / CHOISIR

Choisir la branche et les services.

Depuis le service, ouvrir Déployer. Choisir la branche, comparer le commit en ligne à la référence proposée et relire les services associés. Le périmètre est visible avant de lancer.

main · commit en ligne→release/next · services choisis

Les autres services du même dépôt peuvent être présélectionnés dans « Déployer aussi… ».

03 / CONSTRUIRE

Choisir le build sur VM ou GitHub Actions.

Construire sur la VM, ou confier le build à GitHub Actions et conserver l’image dans GHCR. Deux voies vers le même objectif : une image exécutable du code choisi.

Commit sélectionné→VM ou Actions → GHCR

La voie CI se prépare par des workflows proposés en PR, à relire et intégrer.

04 / PRÉPARER

Vérifier l’image à déployer.

Le Dockerfile et le contexte de build déterminent ce qui entre dans l’image. Avec la voie GitHub Actions, le workflow généré publie une image taguée par commit et fournit sa référence immuable.

Code + Dockerfile→Image du commit choisi

Une image construite n’est pas encore un service déployé.

05 / DÉPLOYER

Lancer le déploiement.

Cliquer sur Déployer pour mettre à jour la sélection. bige-ops exécute l’opération, affiche le job et ses logs. Si une étape échoue, son résultat reste visible pour comprendre où reprendre.

Image prête→Services mis à jour

L’impact dépend du service : ne pas confondre déploiement et garantie de zéro interruption.

06 / CONTRÔLER

Vérifier la version en ligne.

Retrouver le commit déployé, l’état du service et les logs. Au prochain changement, choisir une autre branche et reprendre le même parcours. Redémarrer le service ou ajuster sa capacité restent des actions distinctes.

Job terminé→Commit · état · logs

Contrôler aussi le fonctionnement de l’application après le déploiement.

07 / REDIMENSIONNER

Redimensionner la VM si nécessaire.

Depuis l’inventaire, choisir une nouvelle taille de VM : CPU, mémoire et capacité adaptée au besoin. bige-ops prépare la modification dans la simulation, puis ouvre la revue du plan avant de l’appliquer.

VM · capacité actuelle→Taille cible → plan à confirmer

Questions fréquentes

Doit-on utiliser GitHub Actions et GHCR ?

Non. Le build peut être exécuté sur la VM. GitHub Actions et GHCR constituent une autre route : construire l’image dans la CI, la conserver dans le registre, puis la déployer sur la cible configurée.

bige-ops pousse-t-il directement sur main ?

La proposition de fichiers de build passe par une branche dédiée et une pull request. Le mécanisme refuse de commiter ces changements sur la branche de base. La revue et le merge restent explicites.

Restart et deploy, quelle différence ?

Restart relance le service existant et peut l’interrompre le temps de repartir. Deploy utilise la référence de code choisie pour mettre le service à jour. Aucun de ces gestes n’implique une garantie universelle de déploiement sans interruption.

Ressources, réglages et détails techniques

Les chemins de build, les fichiers proposés et la référence Git font partie du contexte de déploiement.

Le dépôt applicatif contient le code à exécuter. Le dépôt de configuration conserve les simulations et les fichiers d’infrastructure. Une VM ou un cluster constitue la cible d’exécution : ces trois rôles restent distincts.

Ce qui est versionné, et où

DépôtContenuÉcriture par bige-ops
Configuration de la stackSimulation, configuration, Terraform et fichiers générés.Historique et synchronisation GitHub de la configuration.
ApplicationCode métier, Dockerfile, contexte de build.Lecture de la référence choisie ; proposition encadrée de fichiers de build par pull request.

Le build ou le déploiement ne transforme pas le dépôt applicatif en dépôt d’infrastructure. Les détails de l’historique des simulations sont dans GitHub et configuration.

Deux chemins de build

  • Sur VM : le code et son contexte de build servent à construire l’image Docker sur la cible configurée, puis à lancer le service.
  • Dans GitHub Actions : des workflows construisent et scannent l’image, puis la publient dans GHCR après intégration. GHCR conserve l’image ; il ne réalise pas le build.
  • Image déjà publiée : un service peut référencer directement une image, sans cloner un dépôt pour la construire.

Les accès, le Dockerfile et les paramètres de la cible doivent correspondre au mode choisi. Le déploiement sur VM et le déploiement Kubernetes ont leurs propres mécanismes ; le même parcours ne suppose pas Docker Compose sur tous les types de cible.

Le contexte appartient au service

Le dépôt, la référence Git, le sous-dossier et le Dockerfile sont explicites. Dans un monorepo, le contexte permet de désigner la partie utile au service, sans supposer que toute la racine doit être construite.

service_config:
  api:
    git:
      repo: https://github.com/org/monorepo.git
      ref: main
      path: apps/api
      dockerfile: Dockerfile

Le chemin de Dockerfile indiqué dans la configuration est un paramètre de build. Il ne modifie pas, à lui seul, les fichiers du dépôt applicatif.

Proposer les fichiers de build par pull request

bige-ops peut commiter et pousser des fichiers de build dans le dépôt applicatif, sur une branche dédiée, puis ouvrir une pull request. La branche de base n’est pas la cible de ce commit : le mécanisme refuse d’y appliquer directement la proposition.

  • Les fichiers autorisés sont limités au Dockerfile, à .dockerignore, aux presets .bige-ops/ et aux workflows .github/workflows/bige-ops-*.yml.
  • Le reste du code applicatif ne fait pas partie des fichiers inclus par cette opération.
  • La pull request permet de relire le build et la CI avant leur merge.
  • Les workflows proposés publient des images identifiées par commit dans GHCR, selon les accès et la configuration du dépôt.
bige-ops app open-pr --stack <stack> --title "Préparer le build"

Comprendre un échec

Relire le dépôt, la référence, le contexte et le Dockerfile, puis le suivi de l’opération. Un chemin incorrect, une image de base inaccessible ou un secret manquant peuvent bloquer le build. Un build réussi ne garantit pas que le service démarre correctement : ses logs et son état d’exécution restent à consulter.

Le redémarrage d’un service existant ne reconstruit pas son image. Pour changer de code, utiliser le déploiement avec la référence choisie. Aucune garantie générale de déploiement sans interruption n’est déduite de ces commandes.
