01 / COMPOSER

Donner une forme au projet.

Une stack rassemble les services du produit et les ressources qui les font tourner. Dans le Visual, placer l’application, les données et les fichiers, puis choisir leurs machines et leurs connexions. bige-ops traduit cette composition en configuration d’infrastructure : le dessin décrit ce qui sera préparé pour le cloud.

Application + données + fichiers→Une première stack

Une VM est une machine virtuelle. Une stack peut en utiliser une ou plusieurs.

02 / DUPLIQUER

Essayer ailleurs. Garder le point de départ.

Dupliquer la simulation pour créer une variante du même projet. Changer cette copie sans écraser le premier scénario. bige-ops copie la configuration utile et écarte l’état d’exécution et les accès sensibles : explorer une autre architecture ne revient pas à cloner les machines ou les données de production.

Simulation A→A conservée + variante B

La duplication crée un brouillon de configuration, sans nouvelle ressource cloud.

03 / ISOLER

Séparer ce qui n’a pas à être exposé.

Dans la variante, placer les données sur une machine distincte et définir les connexions nécessaires. L’application peut rester accessible au public tandis que sa base utilise un réseau privé. Le Visual rend ce choix lisible : mêmes services, autre répartition des ressources et autre exposition à vérifier avant déploiement.

Application et données regroupées→Application publique + données privées

Un réseau privé et des règles d’accès se configurent ; ils ne se déduisent pas du dessin.

04 / COMPARER

Voir ce qu’un choix change.

Comparer la capacité prévue, l’isolation des services et le coût mensuel estimé de chaque variante. Ajouter une machine ou modifier sa taille change les postes concernés. Le prix vient du catalogue du fournisseur ; les performances réelles se mesureront par des tests, pas par une promesse du simulateur.

Deux architectures possibles→Des différences explicables

Coût estimé, ressources prévues et exposition : trois critères concrets pour choisir.

05 / CONSERVER

Garder les essais. Retrouver les décisions.

Les simulations restent séparées et peuvent conserver leur configuration dans GitHub. Avec un dépôt de configuration connecté, chaque brouillon dispose de sa branche : retrouver une version, garder une alternative et expliquer pourquoi elle a été retenue ou écartée. Cet historique concerne l’infrastructure ; le dépôt du code applicatif reste un autre sujet.

Des variantes locales→Un historique de configuration

La synchronisation GitHub est explicite ; elle n’est pas nécessaire pour commencer à simuler.

06 / PROMOUVOIR

Choisir la stack. Relire ce qui va changer.

Promouvoir la variante retenue vers la simulation live. Si une live existe, bige-ops en sauvegarde d’abord la configuration, puis prépare la nouvelle version en conservant son identité et son état d’infrastructure. Relire ensuite le plan : créations, modifications et suppressions restent à confirmer avant toute application au cloud.

Variante B retenue→Plan de la live à vérifier

Promouvoir prépare la live. Le déploiement demande une action distincte.

Essayer une architecture sans la mettre en production.

Ce qu’une simulation contient

Les services, les machines prévues, les tailles, les volumes, les réseaux et leurs relations. La configuration et son organisation visuelle restent liées : modifier la composition sert à préparer une infrastructure exécutable.

Ce que dupliquer ne fait pas

La copie ne crée pas de VM chez le fournisseur et ne copie pas une base de données. Les états Terraform, les cibles de déploiement et les secrets d’exécution ne sont pas repris dans le brouillon.

Ce qu’il faut pour commencer

L’application et le catalogue disponible permettent de composer et d’estimer sur le poste. Lire le compte cloud, vérifier le plan et déployer demandent ensuite les accès et les permissions adaptés.

Comparer le coût et la manière de faire tourner le produit.

Une machine ou plusieurs

Regrouper les services limite le nombre de ressources. Les séparer permet de choisir leurs tailles et leur exposition indépendamment. Le choix dépend du produit, de ses contraintes et de ce que l’équipe souhaite exploiter.

Des ressources, pas un score magique

CPU, mémoire, volumes et relations réseau décrivent la capacité réservée. Une simulation ne mesure pas les temps de réponse, la charge maximale ou la disponibilité : ces points se vérifient avec des tests.

Un budget décomposable

L’estimation relie les tarifs aux ressources déclarées. Ouvrir son détail pour comprendre un écart entre variantes, les hypothèses mensuelles et les postes encore inconnus.

Conserver les essais. Préparer une seule live.

Deux dépôts, deux rôles

Le dépôt de l’application contient le code à construire. Le dépôt de configuration conserve les choix d’infrastructure. Quand la synchronisation est utilisée, les brouillons suivent des branches sim/* et la configuration live suit main.

Une promotion réversible au niveau de la configuration

Avant de remplacer une live existante, bige-ops crée un snapshot de sa configuration. Si ce snapshot échoue, la promotion s’arrête. Ce mécanisme n’est pas une sauvegarde des bases ou des fichiers applicatifs.

Un plan avant toute action cloud

La promotion ne lance pas l’application du plan. Vérifier ce que le fournisseur va créer, modifier ou supprimer, puis déclencher l’opération. La publication de la configuration live sur GitHub est proposée après un Apply réussi.

Les points à connaître.

Est-ce un environnement de test qui fait déjà tourner mon application ?

Une simulation décrit d’abord une infrastructure. La dupliquer ne démarre aucune machine et ne copie aucune donnée. Lancer une application localement ou sur le cloud est une opération distincte.

Peut-on préparer plusieurs options sans payer plusieurs infrastructures ?

Oui : les variantes de configuration peuvent rester sur le poste. Composer, dupliquer ou estimer ne crée pas de ressources chez le fournisseur. Les ressources déployées, elles, sont soumises à sa facturation.

Une promotion remplace-t-elle immédiatement la production ?

Non. Elle prépare la configuration de la live, avec un snapshot préalable lorsqu’une live existe. Le plan réel doit ensuite être relu et appliqué explicitement ; une promotion seule n’exécute aucun changement cloud.

Ressources, réglages et détails techniques

Les topologies ci-dessous détaillent les ressources possibles. Leur disponibilité dépend du fournisseur et de la stack. Les tailles proposées sont des points de départ, pas des garanties de performance.

Les exemples de cette référence décrivent les points de départ Outscale. Ils préparent une configuration de ressources, de services et de réseau à ajuster dans le Visual. Dupliquer la simulation permet d’explorer une autre topologie avant de la déployer. Le périmètre OVHcloud est détaillé dans les services pris en charge.

Quand réexaminer la topologie

  • D’une machine à l’app et ses données séparées : pour isoler les ressources et les besoins de l’application de ceux de la base. Cette séparation ne constitue pas, à elle seule, une architecture haute disponibilité.
  • Vers Kubernetes managé : pour orchestrer plusieurs workloads et configurer leur capacité. L’autoscaling et la disponibilité demandent une configuration adaptée ; Kubernetes ne les garantit pas par sa seule présence.

Dans les deux cas, tu dupliques ta simulation, tu changes la topologie et tu compares les deux versions (machines, bases, estimation) avant de décider.

Les réglages et opérations associés

  • Le réseau : réseau privé et règles d’ouverture explicites. Vérifier l’exposition des services et des bases dans la configuration retenue. Réseau
  • Les données : depuis le panneau Données, lancer les opérations de sauvegarde, restauration ou migration disponibles pour le moteur et la cible choisis. Object Storage
  • Le HTTPS : configuration du load balancer et du certificat pour les topologies concernées. LBU
  • Les secrets : coffre local et références dans la configuration, avec injection des valeurs nécessaires à l’exécution. Secrets
  • L’estimation et les risques : consulter les coûts estimés et lancer les analyses disponibles avant de déployer. Catalogue de prix

Pour les développeurs

Les mêmes points de départ existent en ligne de commande :

bige-ops add layouts
bige-ops add layout node-app --name mon-app
bige-ops add layout custom --runtime python --db postgres --db redis --web spa --lbu
  • Topologies : single-vm (une machine), multi-vm (app et données séparées), oks (Kubernetes managé, les services deviennent des Deployments). VMs · OKS
  • Taille de la machine unique : sizing.single_vm sur la stack.
  • Les workers partagent la VM de l’app ; en multi-vm, les URLs des bases sont injectées après l’apply (coffre → .env) ; le premier deploy doit être complet avant un --service ciblé.
