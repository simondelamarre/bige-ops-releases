01 · Choix

Choisir le modèle ou l’agent.

Configurer une clé Anthropic, OpenAI, Gemini, Mistral ou OpenRouter dans les réglages, puis choisir un modèle disponible. Autre chemin : relier Codex, Claude Code ou Cursor au serveur MCP local. Le parcours Qwen3 local est proposé lorsqu’il est installé et validé pour les outils.

Fournisseur ou agent→Outils bige-ops accessibles

L’API intégrée et la session d’un client MCP sont deux modes distincts.

02 · Contexte

Partager les notes utiles.

Décrire le produit, la stack, les objectifs et les besoins dans les notes du workspace ou de la simulation. Les notes utiles peuvent être apportées au contexte de l’agent. Une demande ponctuelle suffit aussi ; la mémoire écrite permet surtout de suivre les décisions, de les relire et de les partager.

Intention et notes→Contexte du projet

Le contexte effectivement fourni dépend du parcours et de la sélection ; l’agent ne lit pas automatiquement toutes les notes.

03 · Proposition

Relire la proposition dans la simulation.

Demander une topologie ou un changement de configuration. L’assistant utilise les outils autorisés du produit, puis les validations et la génération. Examiner le résultat dans Visual, relire les coûts estimés et conserver une simulation distincte pour comparer la proposition avant toute décision de production.

Besoin compris→Simulation à examiner

Les commandes sensibles suivent leur confirmation ; une proposition n’est pas une autorisation générale d’agir sur le cloud.

04 · Bilan

Garder un bilan dans les notes.

« Faire un bilan de consommation du mois précédent. » Dans les notes cloud, l’agent peut lire les données d’exploitation disponibles, rédiger un bilan et préparer une présentation. Les informations absentes restent inconnues. Ce parcours de reporting et d’optimisation continue d’être affiné en bêta.

Données du mois→Notes et présentation

Les coûts, métriques et factures disponibles dépendent du fournisseur et des accès du compte.

05 · Décision

Relire une proposition d’optimisation.

Utiliser le bilan pour repérer une ressource surdimensionnée, un manque de capacité ou une dépense à examiner. Consigner la recommandation puis la travailler dans une simulation. Comparer la configuration et son estimation avant de choisir ce qui passera en production.

Hypothèse d’optimisation→Simulation puis décision

Le mode Notes cloud n’exécute pas le déploiement et ne crée pas directement une simulation depuis un bilan.

Choisir comment connecter son agent.

Trois chemins distincts ; aucun n’est nécessaire pour utiliser les fonctions principales de l’app.

Assistant intégré par API

Configurer sa clé Anthropic, OpenAI, Gemini, Mistral ou OpenRouter, puis choisir un modèle du catalogue et les options disponibles. Les appels partent de l’app vers le service choisi. La facturation API relève de ce compte fournisseur.

Modèle local

Un parcours Qwen3 sur CPU utilise llama-server sur le poste, sans clé API. Le modèle doit être installé et ses outils testés sur la machine avant d’être proposé comme agent disponible. Il n’est pas présenté comme équivalent à tous les modèles distants.

Agent habituel par MCP

L’assistant MCP prépare la configuration de Codex, Claude Code ou Cursor vers le CLI local bige-ops. Le client externe gère son modèle, sa session et ses autres permissions. L’app fournit ses outils et les skills du produit dans leur périmètre.

Choisir les outils accessibles.

Une phrase dans un chat n’équivaut pas à une permission générale sur la production.

Lecture et configuration

Les outils lisent le projet autorisé, filtrent les chemins sensibles et appliquent leurs contrats de mutation. Les commandes possibles sont explicitement limitées.

Production et identité

Le canal CLI de l’agent refuse apply, deploy et redeploy directs. Des outils dédiés peuvent préparer une action à confirmer dans l’app. Les PR concernent des fichiers de déploiement autorisés sur une branche dédiée ; le mode Notes cloud ne dispose pas de ces outils.

Historique et erreurs

Les sessions et traces sont conservées localement. Les appels d’outils, leurs résultats et les erreurs donnent un fil de lecture ; une réponse plausible ne remplace pas la vérification du résultat.

Vérifier les données envoyées et le coût.

Utiliser un modèle distant signifie lui transmettre le contexte nécessaire à la demande.

Contexte transmis

Les messages et les éléments de projet utilisés par l’assistant partent vers l’API configurée. Les outils bloquent l’accès aux fichiers de coffre et credentials ; il reste nécessaire de ne pas coller de secret dans une demande.

Clés API et sessions

Les clés de l’assistant intégré sont stockées dans les réglages locaux, distinctement du coffre applicatif. Une session de conversation bige-ops n’est pas un abonnement ChatGPT ou Claude et ne lui donne pas automatiquement accès.

Coûts et disponibilité

Les consommations et coûts disponibles sont affichés ou estimés selon le fournisseur. Les droits du compte et la disponibilité réelle du modèle s’appliquent. Aucun crédit d’usage universel ni quota illimité n’est promis.

Choisir le fournisseur du modèle.

Le fournisseur, les données transmises et les conditions du compte restent des choix explicites.

API configurée dans l’app.

Les appels partent directement vers Anthropic, OpenAI, Google Gemini, Mistral ou OpenRouter selon la sélection. OpenRouter est lui-même un intermédiaire choisi. Les clés API restent dans les réglages locaux.

Un modèle local ou un client externe.

Le parcours local fonctionne sur le poste quand ses prérequis sont réunis. Pour d’autres modèles ou configurations personnalisées, le choix peut passer par le client MCP externe ; une URL API arbitraire n’est pas une option native du catalogue actuel.

Les mots du sujet.

Questions fréquentes

Faut-il un abonnement IA pour utiliser bige-ops ?

Non. Les fonctions principales s’utilisent sans IA. L’assistant intégré peut utiliser une clé API configurée ou le modèle local lorsqu’il est disponible. Un client externe connecté par MCP conserve ses propres conditions d’accès.

L’agent peut-il déployer tout seul ?

Les commandes de production sont bloquées dans le canal CLI de l’agent. Certaines actions sensibles passent par un outil dédié et une confirmation dans l’app. Le mode Notes cloud lit les informations d’exploitation et travaille sur les documents ; il ne déploie pas.

Le modèle voit-il tout mon ordinateur ?

Le contexte de travail et les outils sont limités au périmètre exposé par bige-ops. Ce n’est pas un accès général au poste. Un agent externe peut posséder d’autres outils indépendants : leurs permissions relèvent de son propre environnement.

Ressources, réglages et détails techniques

Distinguer le chat intégré, l’audit approfondi et le serveur MCP local. Leurs outils et leurs modèles ne sont pas interchangeables.

Outils disponibles selon le contexte

  • Lister les simulations du workspace et en créer une nouvelle.
  • Lire le contexte du projet : statut, project.yaml, estimation.
  • Lister et lire les fichiers de la simulation.
  • Éditer project.yaml : mise à jour complète ou patch ciblé.
  • Retirer un composant, ajouter une stack.
  • Lancer des commandes CLI en lecture ou en local : validate, generate, estimate --json, status, plan, diff config, inventory show…
  • Lire la documentation intégrée pour justifier ses choix.
  • Préparer un repo applicatif, lire et écrire un Dockerfile, et ouvrir une pull request dessus.

Commandes refusées dans le canal CLI de l’agent

Commande directe bloquéePortée
apply, deploy, redeployMutations réelles sur ton cloud ou tes workloads
github pushLe push du config-history reste une décision humaine
auth login / auth logoutTouche à tes credentials Outscale
import selectionRéécrit project.yaml depuis l’inventaire live
init --forcePeut effacer un projet existant

Les outils projet filtrent les fichiers de secrets : credentials, coffre, .env, .pem, terraform.tfvars sont filtrés côté outils. Les actions sensibles prévues par un outil dédié passent par une demande de confirmation explicite dans le chat. Le mode Notes cloud se limite aux données d’exploitation en lecture et aux documents ; il ne dispose pas des outils de simulation ou de déploiement.

Dans les dépôts applicatifs

Quand l’agent travaille sur un repo de code, l’écriture est volontairement étroite :

  • fichiers autorisés : Dockerfile, .dockerignore, .bige-ops/* ;
  • toujours sur une branche bige-ops/* ;
  • toujours via une pull request — jamais de commit sur main.

Le partage des rôles entre config-history, repos applicatifs et VMs est détaillé dans repos, VMs & Dockerfiles.

L’audit approfondi des failles (en option)

Sans clé ni IA, bige-ops repère déjà les failles de tes dépôts, sur ton poste : pages ou API accessibles sans contrôle d’authentification détecté, erreurs classiques dans le code, bibliothèques qui ont une faille connue (la méthode). Avec une clé API configurée et le modèle choisi, un audit approfondi peut compléter cette lecture :

  • il relit les pistes déjà repérées : pages ou API accessibles sans contrôle d’authentification détecté, passages de code à risque, pièges connus de ton framework ;
  • il propose une qualification des alertes et des faux positifs, à relire dans le contexte du code ;
  • il classe chaque faille par type, selon le catalogue de référence (CWE), avec son urgence (de P0, la plus urgente, à P3) et son exposition ;
  • chaque faille peut devenir un ticket GitHub (issue) prêt à ouvrir : c’est toi qui l’ouvres, rien n’est corrigé à ta place.

Seuls des éléments de contexte sélectionnés du projet partent, avec ta clé, chez le fournisseur d’IA choisi ; la consommation est facturée sur ton compte chez lui. Comme le chat, l’agent d’audit n’applique rien et ne lit pas tes secrets.

MCP local (Codex / Cursor / Claude Code)

Le binaire embarqué lance bige-ops mcp en stdio. Réglages → Agents / MCP prépare la configuration du client externe installé sur le poste. Les outils sont limités ; les commandes apply, deploy et auth sont refusées dans le canal CLI MCP. Le contexte et les permissions du client externe restent distincts.

Traces

Chaque tour de l’agent est journalisé en JSONL sous chats/traces/ (hors repo). Utile pour l’audit et le debug.

Exposition HTTPS

Pour le HTTPS, l’agent écrit dans project.yaml l’ORN du certificat serveur EIM que tu lui donnes : sur un listener LBU, ou dans expose.tls pour OKS. Le certificat se charge d’abord dans EIM. Voir OKS et LBU.

Comment bien s’en servir

  • Donne une intention et une contrainte : « API + Postgres, une seule VM pour commencer, Région eu-west-2 ».
  • Fais-lui lire le contexte avant d’éditer, puis relance validate et generate.
  • Relis le diff de project.yaml : c’est la référence.
  • Pour l’exposition réseau, vérifie ses choix : ouvrir ou non.
  • Pour modifier directement la configuration : mode expert.

Bon usage

Un co-pilote de configuration. L’agent propose ; tu décides. Un dimensionnement, une règle réseau ou une estimation se relisent avant plan et apply. Ses outils et garde-fous s’enrichissent d’une version à l’autre. La consommation de tokens est facturée sur ton compte chez le fournisseur choisi.
