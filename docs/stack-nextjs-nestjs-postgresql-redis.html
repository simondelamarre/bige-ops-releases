bige-ops Gratuit

Next.js + NestJS + PostgreSQL + Redis sur Outscale

Le choix de nombreuses startups SaaS : Next.js pour le front et le rendu serveur, NestJS pour une API structurée, BullMQ pour les tâches de fond, PostgreSQL pour les données, Redis pour le cache et les files, et un bucket compatible S3 pour les fichiers. Voici cette stack posée sur Outscale par bige-ops, chiffrée ligne par ligne.

En bref. Topologie multi-vm en eu-west-2 : une VM app (Next.js, NestJS, worker BullMQ) derrière un LBU, PostgreSQL et Redis sur deux VMs privées, deux buckets OOS (uploads et backups), un NAT pour la sortie du subnet privé. Estimation bige-ops : 428,06 € HT par mois.

Architecture sur Outscale

  • VM app tinav6.c4r8p2 (4 vCPU, 8 GiB) en subnet public : Next.js sur le port 3000, l’API NestJS sur le 3001 et le worker BullMQ, en conteneurs Docker construits depuis ton dépôt.
  • PostgreSQL 17 sur sa propre VM tinav6.c4r8p2 en subnet privé, disque racine io1 de 60 GiB à 3 000 IOPS (le profil base de bige-ops).
  • Redis 8 sur une VM tinav6.c2r2p3 privée : cache, sessions, files BullMQ.
  • OOS, l’Object Storage compatible S3 d’Outscale : un bucket de 200 GiB pour les fichiers des utilisateurs (le SDK S3 de Node pointe sur l’endpoint OOS régional) et un bucket de 50 GiB pour les backups de PostgreSQL.
  • LBU internet-facing comme seule porte d’entrée, HTTPS par certificat EIM ; un NAT service pour que les VMs privées tirent leurs images.

Le projet utilisé, à reproduire chez toi :

bige-ops init -n stack-nextjs-nestjs-postgresql-redis
bige-ops add layout custom --name app --runtime nodejs --web same --worker \
  --db postgres --db redis --topology multi-vm --lbu
# puis project.yaml ajusté comme ci-dessous
bige-ops validate
bige-ops estimate --json
name: stack-nextjs-nestjs-postgresql-redis
region: eu-west-2
enable_nat: true
components:
- type: stack
  name: app
  topology: multi-vm
  services: [api, web, worker, postgres, redis]
  images: {postgres: 'postgres:17', redis: 'redis:8-alpine'}
  sizing: {app_vm: tinav6.c4r8p2, postgres_vm: tinav6.c4r8p2, redis_vm: tinav6.c2r2p3}
  service_config:
    postgres:
      backup: {enabled: true, oos_bucket: saas-app-backups}
- type: load_balancer
  name: app-web
  scheme: internet-facing
  backend_vms: [app-app]
- {type: oos_bucket, name: saas-app-backups, bucket: saas-app-backups, size: 50, purpose: backups}
- {type: oos_bucket, name: saas-app-uploads, bucket: saas-app-uploads, size: 200, purpose: uploads}

Bases de données : versions, backups, CVE

PostgreSQL. PostgreSQL 18 (supporté jusqu’en novembre 2030), 17 (novembre 2029), 16 (défaut bige-ops, novembre 2028) et 15 (novembre 2027) sont maintenus ; 14 sort du support le 12 novembre 2026. La simulation épingle postgres:17. Source : politique de versions PostgreSQL. Côté durcissement : un rôle applicatif dédié (jamais le superutilisateur), des règles pg_hba.conf limitées au CIDR du Net en scram-sha-256, et des mises à jour mineures régulières (la majeure reste celle que tu épingles).

Redis. La simulation garde redis:8-alpine, le tag par défaut de bige-ops : il suit la dernière Redis 8. Épingle la mineure (par exemple 8.10) si tu veux un build strictement reproductible. Côté durcissement : un mot de passe ou des ACL, le protected mode actif, aucune exposition publique, et les commandes d’administration réservées à un utilisateur dédié (sécurité Redis).

Avec NestJS, Prisma ou TypeORM gèrent le schéma et les migrations ; BullMQ s’intègre via le module de queues NestJS.

Le backup est activé dans la simulation (backup.enabled + bucket OOS) : bige-ops crée le bucket, protégé contre la destruction, et prépare backup.sh (bucket, endpoint, planning) où tu branches le dump. Sans backup, Visual, preflight et plan te le signalent. Détail : OOS & backups.

Exposition : ce qui est ouvert, et à qui

  • Une seule entrée publique : le LBU internet-facing. Ajoute-lui un listener HTTPS 443 avec le server_certificate_id (ORN d’un certificat chargé dans EIM) vers le port 3000 de la VM app ; le TLS se termine sur le LBU.
  • VM app en subnet public : avec un LBU, ses ports applicatifs (ceux de tes services : 3000, 3001, 8000, 8080…) n’acceptent que le CIDR du Net (10.0.0.0/16), donc le trafic applicatif passe par le LBU. Sa première IP publique est offerte et sert au deploy SSH.
  • Bases en subnet privé, sans IP publique, chacune derrière son security group qui n’accepte que le CIDR du Net sur son port. Jamais de listener LBU, d’IP publique ni de règle 0.0.0.0/0 vers une base : pour l’administrer, passe par un tunnel SSH via la VM app.
  • Security group de la VM app : il ouvre SSH (22) pour le deploy, ainsi que HTTP (80) et HTTPS (443). Resserre SSH sur tes CIDR connus avant la production, et fais écouter ton app sur un port applicatif (3000, 8000, 8080…), que seul le Net atteint.
  • NAT service : la sortie Internet du subnet privé (images, mises à jour), sans aucune entrée.

Rappel Outscale : deux VMs d’un même subnet se parlent sans passer par les security groups ; séparer l’app (public) et la data (privé) les remet dans le chemin. Détail : réseau · ouvrir ou non, security groups Outscale.

Vulnérabilités : ce que bige-ops vérifie

Avec ta clé API OpenCVE (Settings), l’onglet Vulnérabilités lit ta simulation : chaque composant reconnu, image Docker ou package, est rapproché de sa fiche fournisseur / produit, à raison d’une requête par produit. Les CVE remontées sont classées par risque :

  • Sévérité : score CVSS (critique dès 9, haute dès 7, moyenne dès 4), relevée au moins à « haute » quand la faille figure au catalogue KEV des vulnérabilités exploitées.
  • Exposition dans ta simulation : un composant joignable depuis Internet ou derrière le LBU garde sa sévérité ; un composant en subnet privé descend d’un cran, sauf s’il est KEV.
  • Départage : à risque égal, KEV d’abord, puis CVSS, puis EPSS. Un filtre « important » ne garde que KEV ou CVSS ≥ 7.

Le rapprochement se fait au niveau du produit : tu recoupes ensuite avec la version que tu as épinglée. Une image en latest ressort en plus comme « version non épinglée ». Le résultat est mis en cache dans la simulation et se rafraîchit à la demande.

Mode direct, sans clé : routes Next.js (route handlers, pages/api) et NestJS (@Controller, @Get, @UseGuards), failles de code et XSS front, dépendances npm rapprochées d’OSV. Détail : Node.js sur Outscale.

bige-ops advanced va plus loin avec ta propre clé LLM : un agent d’audit reprend les pistes pré-mâchées (routes ouvertes, motifs à risque, pièges connus du framework), confirme les vraies failles, écarte les faux positifs et classe chaque trouvaille par CWE, avec sa priorité (P0 à P3), son exposition et une issue GitHub proposée. Les appels partent de ton poste ; ni apply, ni lecture des secrets. Voir l’assistant IA.

Ce que bige-ops vérifie avant le deploy

  • bige-ops validate : structure du projet, services custom (image ou dépôt requis), listener HTTPS refusé sans ORN de certificat EIM, et rappel du NAT dès qu’une VM privée existe (c’est lui qui permet docker pull et apt depuis le subnet privé).
  • bige-ops preflight : clés Outscale présentes, OMI résolue, stack déclarée, IP des hôtes après l’apply, Dockerfile trouvé, secrets de build et d’exécution présents dans le coffre, jeton GitHub pour les dépôts privés, et alerte si une base n’a pas de backup vers OOS. Une erreur bloque le deploy.
  • bige-ops plan : le plan Terraform avant tout apply, avec les risques de perte de données signalés ; les buckets OOS sont protégés contre la destruction.
  • Vulnérabilités : composants de la stack confrontés à OpenCVE et classés par exposition, tags latest signalés, dépôts analysés en mode direct.

OpenCVE, le référentiel CVE de bige-ops

Pour savoir quelles vulnérabilités touchent les briques de ta stack, bige-ops s’appuie sur OpenCVE. OpenCVE agrège les CVE publiées (NVD, MITRE, catalogue KEV de la CISA…), les enrichit avec les scores CVSS et EPSS et les range par fournisseur et par produit, consultables dans son explorateur. Le projet est open source : son code, ses issues et les contributions de sa communauté vivent sur GitHub, et il s’installe aussi chez toi. Merci à ses mainteneurs et à tous ceux qui font vivre ce référentiel : c’est grâce à eux que chaque composant de ta simulation a sa fiche CVE à jour.
