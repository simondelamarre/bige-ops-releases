01 / SÉPARER LES USAGES

Séparer les accès du cloud des secrets de l’app.

Les identifiants cloud permettent à bige-ops de piloter le compte choisi. Le token GitHub relie les dépôts ; une clé IA active le fournisseur sélectionné. Les mots de passe des bases et les secrets applicatifs appartiennent au coffre du projet. Chaque famille répond à un besoin distinct.

Accès aux comptes→Secrets du projet séparés

Les accès sont conservés localement puis utilisés pour s’authentifier auprès du service concerné.

02 / RENSEIGNER LE COFFRE

Renseigner la valeur dans le coffre.

La configuration décrit les variables et leurs usages sans y recopier les valeurs sensibles. Dans le coffre, ajouter un secret, repérer une valeur manquante ou résoudre un conflit. Les mots de passe techniques pris en charge peuvent être générés ; les clés d’un fournisseur externe restent à fournir.

Variable référencée→Valeur locale renseignée

Le coffre et le fichier d’environnement local sont exclus de l’historique Git de configuration.

03 / DONNER LA BONNE VALEUR

Fournir le secret au service.

Au déploiement, bige-ops prépare les valeurs nécessaires au build ou à l’exécution selon la configuration. Un accès de déploiement et un secret de conteneur ne sont pas interchangeables. Les mêmes clés peuvent être partagées entre les services d’une simulation sans multiplier les copies manuelles.

Coffre du projet→Valeur utilisée par le service

La nouvelle valeur suit le cycle de build, de déploiement ou de rechargement du service.

04 / RELIER LE COFFRE D’ÉQUIPE

Connecter le Vault de l’équipe.

Pour synchroniser les secrets applicatifs, renseigner l’adresse du serveur HashiCorp Vault, le moteur KV v2 et le chemin du projet. Ajouter le namespace lorsque le serveur l’exige. bige-ops lit et écrit les valeurs selon les droits du token configuré sur le poste. Pour la CI, activer séparément l’envoi vers GitHub Actions Secrets.

Coffre local→Vault KV v2 ou GitHub Actions

Le coffre local reste le point de travail. Chaque destination distante s’active séparément.

Choisir où conserver chaque accès.

Le coffre applicatif ne doit pas devenir le nom générique de tous les identifiants.

Comptes cloud

Les credentials du compte cloud sélectionné sont conservés dans le workspace local. Ils servent aux appels vers le fournisseur. Ils ne sont pas placés dans le dépôt de configuration.

GitHub et services IA

Le token GitHub et les clés API IA sont enregistrés dans les réglages locaux de l’app. La connexion GitHub utilise le Device Flow : la validation s’effectue chez GitHub, puis l’app conserve le token sur le poste.

Secrets applicatifs

Le coffre du projet contient les valeurs attendues par les services : connexion à une base, mot de passe, JWT ou clé utilisée par l’application. La simulation et la production peuvent avoir des valeurs distinctes.

Connecter le coffre de l’équipe.

Choisir où les secrets applicatifs doivent être disponibles. Le coffre local reste actif et chaque synchronisation distante est optionnelle.

HashiCorp Vault KV v2 · bêta

Utiliser le serveur de l’entreprise. Dans Coffre → Sync distante, renseigner son adresse, le moteur KV v2, le préfixe du projet et le namespace si nécessaire. Le token reste dans les réglages du poste. Les droits de ce token déterminent les lectures et écritures autorisées.

Comprendre HashiCorp KV v2 ↗

Local

Le coffre applicatif est un fichier privé du projet. Un bloc de fichier .env est matérialisé pour les usages locaux et le déploiement. Les fichiers sont écrits avec des permissions réservées au propriétaire ; ce stockage n’est pas un chiffrement au repos.

GitHub Actions

Envoyer les secrets applicatifs vers Actions Secrets dans le dépôt choisi. bige-ops chiffre les valeurs avec la clé publique fournie par GitHub avant de les transmettre à l’API.

1Password, Bitwarden ou un autre coffre

Renseigner dans le coffre bige-ops les valeurs que l’équipe autorise à utiliser dans le projet. L’équipe continue de gérer les droits et les rotations dans son outil. Cette saisie est manuelle.

Vérifier quand le secret est utilisé.

Savoir quand une valeur est consommée fait partie de la configuration.

Build et runtime

Une variable intégrée dans une image ou dans un bundle web n’a pas la même confidentialité qu’un secret fourni à l’exécution. Le coffre distingue les phases ; un préfixe de variable ne transforme pas un secret en donnée publiable.

Clés partagées entre services

Une clé commune à plusieurs services d’une simulation peut avoir une entrée commune. Ce partage interne ne signifie pas qu’un coffre d’équipe distant est actif.

État et conflits

Une clé requise absente ou des valeurs anciennes en conflit sont visibles avant le déploiement. La synchronisation et son résultat se relisent ; une sauvegarde locale réussie n’est pas une preuve que toutes les destinations distantes ont accepté la mise à jour.

Dans l’app

Configurer le Vault de l’équipe.

Dans les options du Coffre, ouvrir Sync distante. Indiquer l’adresse du serveur Vault, le namespace si nécessaire, le moteur KV v2 et le chemin du projet. Le token est renseigné séparément dans les réglages locaux.

Questions fréquentes

Où sont conservés les identifiants et les secrets ?

Les identifiants cloud, GitHub et IA sont enregistrés localement et servent à authentifier les appels vers le service choisi. Les secrets applicatifs vivent dans le coffre du projet et sont fournis aux services qui en ont besoin lors du déploiement. Une synchronisation optionnelle permet aussi de les envoyer vers GitHub Actions ou un serveur Vault configuré.

Peut-on utiliser un autre coffre d’entreprise ?

Les valeurs autorisées peuvent être renseignées manuellement dans le coffre du projet. Le connecteur de coffre d’équipe intégré cible HashiCorp Vault KV v2. GitHub Actions Secrets sert à alimenter la CI.

Le coffre local est-il chiffré ?

Les fichiers applicatifs sont enregistrés localement avec des permissions réservées au propriétaire. Le coffre local n’est pas un coffre chiffré au repos. La protection de la session, du disque et des sauvegardes du poste reste nécessaire.

Modifier un secret change-t-il immédiatement la production ?

L’enregistrement met à jour le coffre local et les destinations de synchronisation activées. L’application déployée utilise la nouvelle valeur après le build, le redéploiement ou le rechargement prévu par son fonctionnement.

Ressources, réglages et détails techniques

Références de configuration et destinations effectives des identifiants. Les secrets applicatifs, les credentials cloud et les tokens des services ne partagent pas tous le même emplacement ni le même cycle de vie.

Solutions actuelles

Le coffre local (vault.local.json) est toujours la source primaire sur ta machine. En option, tu peux synchroniser vers des backends que tu contrôles — rien n’est imposé.

BackendRôleStatut
Local Coffre sur le poste → génère .env au deploy Local · source primaire
GitHub Actions secrets Pousse les secrets vers un repo que tu choisis (API Actions) Bêta · sync optionnelle
HashiCorp Vault KV v2 (mount + path) sur le serveur Vault configuré — token local ; recette réelle restant à valider Bêta · sync optionnelle

Config non secrète : bige-ops/vault.config.json. Tokens (GitHub / Vault) : Settings desktop, machine-local. Jamais de vault SaaS bige-ops au milieu.

Le coffre local alimente les services au build ou au déploiement selon la configuration. Les fichiers sensibles sont exclus du suivi Git prévu par bige-ops ; une synchronisation Actions Secrets utilise une API distincte et ne crée pas de commit contenant les valeurs.

Ce qui n’est jamais poussé sur le config-history

Le dépôt config-history versionne la stack, pas tes secrets. Sont exclus du push :

  • les fichiers de credentials Outscale
  • vault.local.json, .env
  • terraform.tfvars et les tfstate
  • les *.pem (clés SSH)
  • l’inventaire, .app-src/, .state/

Le reste de bige-ops/ — project.yaml, Terraform généré, specs OKS, compose — est versionné normalement. C’est justement l’intérêt : un historique lisible et partageable avec exclusion des fichiers sensibles connus. Ne pas recopier une valeur secrète dans un document suivi.

Secrets de build

La clé build.secrets déclare les secrets nécessaires à la construction des images Docker (token de registry privé, token de package…). Ils ne sont pas écrits en dur : ils sont injectés au moment du deploy depuis le coffre. Voir repos, VMs & Dockerfiles. 

bige-ops/
  vault.local.json      # coffre — jamais pushé
  .env                  # généré au deploy — jamais pushé
  terraform/
    terraform.tfvars    # clés API + image_id — jamais pushé

Après le deploy

Une fois la stack déployée, les secrets d’exécution vivent là où tourne l’application : variables d’environnement ou fichiers fournis au service selon le parcours. L’adoption explicite de certains mots de passe runtime pris en charge est un mécanisme distinct. Le changement d’une valeur du coffre ne garantit pas une rotation immédiate de tous les services déjà déployés.

Ce que couvre le coffre

Ce que bige-ops ne fait pas. Pas de chiffrement applicatif du coffre au-delà des permissions du système de fichiers, pas de rotation automatique, pas de gestion universelle des droits d’une équipe ni d’audit d’accès fin. Les sync GitHub / HashiCorp utilisent les destinations activées ; HashiCorp KV v2 peut lire puis réécrire les valeurs locales — ce n’est pas un Secrets Manager entreprise clé en main. Les outils projet de l’assistant IA filtrent ces chemins sensibles. Ne pas coller de secret dans une conversation ou un document destiné au modèle.
