OKS & pods

OKS (OUTSCALE Kubernetes as a Service) est le Kubernetes managé d’Outscale : Outscale opère le control plane, tu dimensionnes les nodepools et les workloads. bige-ops génère les specs du cluster et les manifests, puis les applique avec les outils officiels.

Avant de commencer. OKS est disponible dans les Régions eu-west-2 et cloudgouv-eu-west-1 (SecNumCloud), et s’active sur demande auprès du support Outscale (support@outscale.com). Tu peux simuler et estimer un cluster sans cela ; l’activation compte au moment de l’apply. Détail : régions & accès aux services.

Ce qu’OKS t’apporte

  • Un control plane managé : Outscale le met à jour, le patche et le remplace si besoin. Ses nœuds peuvent donc changer d’IP : n’écris pas de règle de pare-feu sur leurs adresses.
  • Des versions récentes : OKS prend en charge Kubernetes 1.32 à 1.36. Un cluster existant ne monte pas de version tout seul : la mise à jour se déclenche quand tu le décides.
  • Des workers jetables : les nœuds des nodepools n’apparaissent pas comme des VMs dans ton compte. C’est voulu : un cluster se traite comme une infrastructure reproductible, pas comme des machines entretenues à la main.
  • Des load balancers natifs : un Service de type LoadBalancer crée un LBU, et des annotations OKS permettent d’en répartir sur plusieurs Subregions pour la haute disponibilité.

Choisir le control plane

TypeMastersHAÉchelle indicative
cp.mono.master1 × 4 GiBnonjusqu’à 10 nœuds
cp.3.masters.small3 × 4 GiBouijusqu’à 50 nœuds
cp.3.masters.medium3 × 8 GiBouijusqu’à 200 nœuds
cp.3.masters.large3 × 16 GiBouijusqu’à 400 nœuds

bige-ops part sur cp.mono.master et Kubernetes 1.34 : le bon choix pour simuler, tester ou monter un cluster éphémère. Pour la production, Outscale recommande un control plane à 3 masters (le mono-master n’a ni HA ni SLA). On peut passer de cp.mono.master à un type supérieur après création, pas l’inverse. Et l’échelle dépend aussi du nombre d’objets Kubernetes et de leur activité : un petit cluster très chargé peut demander un control plane plus grand.

App, CLI bige-ops, oks-cli, kubectl

Chemin nominal : l’app desktop (Visual / Workspace). Sous le capot, ou en terminal : la CLI bige-ops, même moteur. Pour OKS :

  • apply --target oks → oks-cli : projet, cluster, nodepools, kubeconfig.
  • deploy → kubectl apply sur oks/apps/.

Détail : CLI · app · OKS.

Cluster et nœuds

Une topologie oks déclare le cluster, la version Kubernetes, le control plane et les nodepools (type Tina, nombre de nœuds, Subregion). Le formulaire Visual (ou bige-ops add …) met à jour la simulation immédiatement. À l’apply, l’accès admin au cluster est restreint à ton IP publique (/32), ou au CIDR que tu fixes dans OKS_ADMIN_CIDR.

Pods et réplicas

Les services (api, web, worker, bases…) deviennent des Deployments sous oks/apps/. Le champ réplicas (service_config.*.replicas) de l’inspector réécrit le setup directement. Par défaut : api et web à 2, worker et bases à 1. Puis deploy applique via kubectl. Réplicas ≠ exposition réseau : pour ouvrir ou non un Service, voir réseau · ouvrir ou non. 

service_config:
  mongodb:
    replicas: 1
  api:
    replicas: 2
    hpa:
      enabled: true
      min: 2
      max: 8
      target_cpu: 70
    memory_mb: 512

Leviers de scale : réplicas fixes, HPA sur le CPU (services sans état), mémoire par pod, nombre et type de nœuds par nodepool (formulaires Visual, puis generate).

Les bases déployées en pods démarrent sur un volume emptyDir : leurs données vivent avec le pod. Le filet de sécurité, c’est le backup vers OOS.

HTTPS public : Service LoadBalancer avec expose.tls.server_certificate_id, l’ORN d’un certificat serveur EIM. Le LBU créé par OKS termine le TLS, sans Ingress ni cert-manager à maintenir.
