01 · SCANNER

Choisir le dépôt et la branche.

Choisir le dépôt et la branche. bige-ops analyse les fichiers accessibles, repère les routes et inspecte les dépendances. Chaque résultat conserve le commit qui l’a produit.

Dépôt + branche→Code et dépendances analysés

Code, routes et composants détectés restent rattachés au périmètre analysé.

02 · CARTOGRAPHIER

Cartographier les routes et les composants.

Le graphe relie services, fichiers, routes et composants. Suivre une relation pour retrouver le code concerné ; parcourir l’arbre ou filtrer les routes par langage et framework pour examiner le point d’entrée.

Services dispersés→Un graphe navigable

La cartographie montre les relations reconnues par le scan.

03 · LOCALISER

Localiser la faille dans le graphe.

Une faiblesse de code pointe vers son fichier et sa ligne. Une CVE revient au paquet ou à l’image et à la version concernée. Ouvrir le résultat pour lire les éléments observés et la correction proposée.

Une alerte→Une source et des éléments vérifiables

CWE : faiblesse du code. CVE : vulnérabilité connue liée à un composant.

04 · QUALIFIER

Vérifier si elle est exposée.

Rapprocher la route détectée, ses contrôles d’accès et l’exposition du service. Une API publique et un composant interne ne portent pas la même surface d’attaque. Cette lecture aide à prioriser les CVE applicables.

CVE + service→Version + route + exposition

L’exposition est issue du code et de la configuration. Privé ne signifie pas corrigé.

05 · APPROFONDIR

Qualifier les alertes avec le Deep Agent.

Lancer le Deep Agent intégré pour relire les extraits et les routes signalés. Il qualifie les résultats et écarte les faux positifs identifiés avec une explication, pour concentrer la revue sur les problèmes étayés.

Signaux du scan→Résultats qualifiés + motifs de rejet

Audit IA optionnel, sur le contexte transmis ; la revue reste nécessaire.

06 · TRANSMETTRE

Ouvrir une issue avec les preuves.

Depuis une faille, créer l’issue GitHub sur le dépôt concerné. Localisation, commit, contexte et piste de correction l’accompagnent. Le lien reste associé au résultat pour retrouver le travail engagé.

Faille sélectionnée→Issue GitHub documentée

Accès GitHub requis. Les PR de l’agent couvrent les fichiers de déploiement autorisés.

07 · RECONTRÔLER

Relancer le scan après correction.

Après la correction, relancer le scan et les tests sur la nouvelle version. Retrouver le code, les versions et les résultats du bon commit pour décider de la suite avec des éléments à jour.

Correction du code ou du paquet→Nouvelle analyse du commit

Une issue ouverte n’est pas une faille corrigée ; le recontrôle ferme la boucle.

Retrouver la route et la ligne de code.

Naviguer dans le résultat avec les repères du projet.

Les routes, dans leur service

Retrouver les routes détectées par langage et framework, leur fichier et les contrôles d’accès identifiés. Express, FastAPI, Django, Gin ou Rails : la couverture dépend des conventions reconnues.

Le code, à son emplacement

Une faiblesse conserve le fichier, la ligne, le fragment concerné et la raison de l’alerte. Le graphe et l’arbre permettent de revenir à ce contexte sans chercher dans une liste déconnectée.

Les dépendances, à leur version

Comparer la version observée aux plages affectées, lire les références disponibles et examiner une version corrigée candidate. OSV et OpenCVE enrichissent cette lecture.

Qualifier les failles dans leur contexte.

Gravité, applicabilité et exposition répondent à trois questions différentes.

Est-ce la version affectée ?

Distinguer une correspondance de catalogue d’un résultat applicable à la version analysée. Les états candidat, corrigé ou non affecté évitent de traiter chaque mention comme une urgence.

Quel chemin mène au service ?

Relier le signal aux routes détectées et au réseau public, privé ou encore inconnu. Le contexte aide à prioriser ; il ne remplace pas un test d’exploitation.

Que reste-t-il après l’audit ?

Le Deep Agent relit annotations, routes et extraits. Les faux positifs identifiés sont accompagnés d’un motif ; les résultats étayés gardent leurs preuves. Aucun audit ne garantit zéro faux positif.

Préparer une issue ou une PR.

Une action traçable, depuis le résultat qui l’a déclenchée.

Créer l’issue depuis la faille

L’issue reprend le contexte technique sur le bon dépôt. Son lien reste enregistré dans l’app ; les résultats qui partagent une remédiation peuvent être regroupés.

Ouvrir une PR avec l’agent

L’agent peut proposer une PR pour les fichiers de déploiement autorisés : Dockerfile, .dockerignore et .bige-ops. L’ouverture est confirmée ; le code applicatif n’est pas réécrit automatiquement pour chaque CVE.

Dans l’app

Une CVE ne s’arrête pas à son numéro.

Le détail rapproche paquet, version, plage affectée et références. Les éléments encore inconnus restent visibles pour guider la qualification.

Les mots du sujet.

CWE
Famille de faiblesse dans le logiciel : injection, contrôle d’accès insuffisant ou autre défaut de conception ou de code.
CVE
Identifiant d’une vulnérabilité connue. Sa présence dans un catalogue ne suffit pas à établir qu’une version est affectée.
OSV
Base de vulnérabilités qui relie des paquets et versions à des avis de sécurité.
Exposition
Contexte d’accès au service : public, privé ou inconnu. Il aide à prioriser sans remplacer l’analyse du code.
Remédiation
Action pour traiter un problème : corriger, mettre à jour, réduire l’exposition ou documenter une investigation.
Faux positif
Alerte qui, après examen du contexte, ne décrit pas une faiblesse applicable au cas analysé.

Questions fréquentes

Faut-il utiliser une IA pour analyser une stack ?

Non. Le scan de base fonctionne sans IA obligatoire. Le Deep Agent est un audit optionnel : il examine les annotations, routes et extraits transmis pour qualifier les résultats et écarter les faux positifs identifiés.

Est-ce que toutes les alertes sont des failles exploitables ?

Non. Les résultats distinguent ce qui est observé, applicable, candidat ou encore inconnu. Les heuristiques de code et les correspondances de catalogue exigent une qualification. L’absence d’alerte n’est pas une garantie de sécurité.

Peut-on créer une issue ou une PR depuis bige-ops ?

Une faille permet de créer directement une issue GitHub documentée, avec les accès adaptés. Les PR de l’agent concernent les fichiers de déploiement autorisés et demandent confirmation. Il n’existe pas de correction automatique universelle du code ou de toutes les CVE.
