Vulnérabilités

01 · Périmètre

Cartographier la stack et son code.

Partir des services déclarés et des dépôts qui leur sont reliés. Choisir la branche à analyser. Les fichiers, les composants détectés et les résultats restent rattachés au commit lu : une autre branche garde son propre état d’analyse.

Services et dépôts→Périmètre analysé

La couverture dépend des langages, frameworks, fichiers accessibles et limites de scan.

02 · Routes

Voir les portes d’entrée.

Retrouver les routes détectées par langage et framework, puis remonter au fichier et au service. Distinguer l’exposition publique, privée ou encore inconnue. Cette lecture rapproche les chemins de l’API de la stack réelle, au lieu de traiter toutes les routes comme accessibles sur Internet.

Code et frameworks→Routes et exposition

TypeScript/JavaScript, Python, Go, PHP et Ruby disposent de règles de découverte ; la couverture varie selon les frameworks.

03 · Faiblesses

Localiser ce qui pose problème.

Examiner les alertes sur le code, les contrôles d’accès et les secrets détectés. Une faiblesse classée CWE conserve son emplacement et les éléments qui ont déclenché l’alerte. Ouvrir le fichier ou la route permet de comprendre le signal avant de décider quoi corriger.

Route ou fichier→Faiblesse localisée

Une heuristique est un signal à qualifier, pas la preuve automatique d’une exploitation.

04 · Dépendances

Relier les versions aux CVE.

Inspecter les paquets et images identifiés dans le périmètre. OSV aide à comparer les dépendances avec les versions affectées ; OpenCVE enrichit les composants reconnus. Conserver la version observée, la plage concernée et les informations disponibles sur une correction.

Images et paquets→Versions concernées

Une correspondance de nom d’image ne démontre pas que son contenu installé est vulnérable.

05 · Priorité

Traiter le risque dans son contexte.

Rapprocher la gravité, l’applicabilité et l’exposition de la stack. Une route publique, un service privé et une exposition inconnue ne décrivent pas la même situation. Regrouper les CVE qui partagent une correction et distinguer les résultats applicables des candidats ou des éléments déjà corrigés.

Alerte et exposition→Priorité à examiner

Un réseau privé réduit l’exposition ; il ne corrige pas une vulnérabilité.

06 · Action

Créer une issue qui permet d’avancer.

Depuis le résultat, créer une issue GitHub avec le dépôt, le commit, la localisation et l’action proposée. Le lien reste attaché à l’alerte. Corriger le code ou la dépendance dans le parcours de développement, puis relancer le scan et les tests sur la version obtenue.

Résultat qualifié→Issue liée au commit

Le scan crée des issues. Les PR de l’agent concernent les fichiers de déploiement autorisés, pas une correction automatique de toutes les CVE.

Une route, un langage, un fichier.

La cartographie relie la structure du projet au code effectivement analysé.

Des points d’entrée concrets.

Express, Fastify, NestJS, FastAPI, Flask, Django, Gin, Laravel ou Rails : les règles reconnaissent des conventions propres aux frameworks. Les routes dynamiques ou non reconnues restent une limite de couverture.

L’authentification mérite une vérification.

Un contrôle détecté, absent ou inconnu fournit un point de départ pour l’audit. Le code et le chemin d’exécution déterminent la protection réelle ; le nom d’une route ne suffit pas.

Rester sur le bon commit.

Un résultat garde son dépôt, sa branche et son commit. La correction doit être rescannée sur le code obtenu, sans réutiliser comme preuve un ancien résultat d’une autre branche.

Toutes les alertes ne racontent pas le même problème.

La page doit permettre de lire le résultat sans être expert des acronymes.

CWE : une faiblesse dans le code

Une requête construite avec une entrée utilisateur, une route mal protégée ou une gestion risquée des données relève d’une famille de faiblesse. Le résultat doit conserver son fichier, sa ligne et la raison de l’alerte.

CVE : une vulnérabilité connue

Le nom du paquet ne suffit pas. La version observée, la plage affectée et les éléments disponibles sur la correction déterminent si une vulnérabilité connue peut concerner le projet.

Secrets et configuration

Une valeur sensible présente dans le code ou une exposition mal comprise demande une action différente d’une mise à jour de dépendance. Les catégories restent séparées pour préparer la bonne intervention.

Relier le résultat à ce qui est vraiment exposé.

Le même signal n’a pas la même priorité selon l’endroit où il apparaît.

Le bon dépôt, le bon commit

Les routes et résultats restent liés au périmètre analysé. Revenir sur une autre branche ne doit pas mélanger ses données avec celles d’une analyse précédente.

Une route et son exposition

L’arbre et le graphe permettent de remonter au service, au fichier et à la route. Une exposition Internet, privée ou inconnue est conservée comme contexte, sans transformer une incertitude en confirmation.

Le triage plutôt que le bruit

Les résultats applicables, candidats, corrigés ou non affectés ne sont pas présentés comme également urgents. Les filtres permettent de revoir le catalogue complet sans perdre la sélection de travail.

OSV, OpenCVE et une démonstration lisible.

Les sources renforcent le contexte. Elles ne remplacent pas la preuve dans le projet.

OSV : comparer les versions

Le scan utilise les avis disponibles pour relier les dépendances à leurs plages affectées et à des versions corrigées candidates. Un manifeste peut décrire une intention ; la version réellement résolue compte pour conclure.

Une issue avec ses éléments

Le brouillon rassemble la localisation, le commit, les éléments observés, l’impact et l’action proposée. Les failles qui partagent une correction peuvent être regroupées plutôt que multiplier les tickets sans contexte.

Issue et PR : deux actions distinctes.

Le parcours Vulnérabilités crée une issue documentée. L’agent sait ouvrir une PR confirmée pour les fichiers de déploiement autorisés — Dockerfile, .dockerignore et .bige-ops — sur une branche dédiée. Il ne promet pas de réécrire arbitrairement le code applicatif pour résoudre chaque alerte.

Corriger puis recontrôler

Une version suggérée est une candidate. Après une modification, relancer le scan et les tests sur la version effectivement obtenue. La création d’une issue n’a pas valeur de correction.

Approfondir avec l’IA, au besoin

Le Deep audit est un parcours optionnel : modèle, effort et volume de contexte sont choisis. Il complète le scan à partir des annotations et routes transmises, sans rendre l’IA obligatoire ni garantir l’absence de faux positifs.

Les licences demandent leur propre revue.

Choisir une stack, c’est aussi vérifier les conditions d’usage de ses composants.

SSPL et autres licences

La licence peut compter dans une décision d’hébergement ou de distribution. Elle ne doit pas être colorée comme une vulnérabilité ni confondue avec une CVE.

Un périmètre explicite

Le scan de sécurité présenté ici n’est pas un audit juridique ni une certification de conformité des licences. La revue s’effectue selon les composants et l’usage envisagé.

Les mots du sujet.

CWE
Famille de faiblesse dans le logiciel : injection, contrôle d’accès insuffisant ou autre défaut de conception ou de code.
CVE
Identifiant d’une vulnérabilité connue. Sa présence dans un catalogue ne suffit pas à établir qu’une version est affectée.
OSV
Base de vulnérabilités qui relie des paquets et versions à des avis de sécurité.
Exposition
Contexte d’accès au service : public, privé ou inconnu. Il aide à prioriser sans remplacer l’analyse du code.
Remédiation
Action pour traiter un problème : corriger, mettre à jour, réduire l’exposition ou documenter une investigation.
Faux positif
Alerte qui, après examen du contexte, ne décrit pas une faiblesse applicable au cas analysé.

Les points à connaître.

Faut-il utiliser une IA pour analyser une stack ?

Le scan de base fonctionne sans IA obligatoire. Un audit approfondi assisté peut compléter l’analyse ; il ne remplace ni les preuves du scan, ni la revue, ni les tests de correction.

Est-ce que toutes les alertes sont des failles exploitables ?

Non. Les résultats distinguent ce qui est observé, applicable, candidat ou encore inconnu. Les heuristiques de code et les correspondances de catalogue exigent une qualification. L’absence d’alerte n’est pas une garantie de sécurité.

Une issue GitHub corrige-t-elle le problème ?

Non. Elle rassemble les éléments pour le traiter : dépôt, commit, emplacement, contexte et action proposée. L’équipe relit, corrige puis teste et relance l’analyse. Les résultats d’une correction ne sont pas déduits de la seule création d’un ticket.
