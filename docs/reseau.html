bige-ops Gratuit

Réseau · ouvrir ou non

Ouvrir un pod, une VM, ou seulement une face d’un layout multi-VM se décide à deux niveaux : les règles de ton projet (simulation, YAML) et les règles Outscale (Net, subnets, security groups, LBU).

Principe court. Expose le minimum : une entrée publique (LBU en HTTP ou HTTPS) quand il en faut une ; data et administration en privé. Réserve SSH et les ports d’admin à des CIDR connus, jamais à 0.0.0.0/0 par confort.

Ce qu’on ouvre, ou pas

  • Face publique d’un layout VMs — la VM app, derrière le LBU. Les ports applicatifs sont servis par le load balancer, pas toute la machine.
  • VM data et bases — subnet privé, sans IP publique. Les security groups générés pour les bases n’acceptent que le CIDR du Net.
  • Pod OKS — Service selon le besoin ; réplicas ≠ exposition. L’API Kubernetes est restreinte à ton IP ou au CIDR de OKS_ADMIN_CIDR.
  • SSH et deploy — sur la face app si nécessaire ; jamais sur une base « ouverte pour dépanner ».

Ce que fait le réseau Outscale

  • Le Net est ton réseau privé dans une Région. Son CIDR, pris dans les plages RFC 1918, va de /16 à /28 et ne se modifie plus après création : bige-ops part sur un /16 pour garder de la marge.
  • Les subnets vivent dans une Subregion. Outscale réserve les quatre premières adresses et la dernière de chacun (réseau, routeur, DNS, réserve, broadcast).
  • Les security groups d’un Net filtrent au niveau de la VM, en entrée comme en sortie, et une règle peut viser un autre security group plutôt qu’un CIDR.
  • Le firewall bypass : par défaut, deux VMs du même subnet se parlent sans passer par les security groups, pour gagner en latence. Séparer l’app (subnet public) et la data (subnet privé), comme le fait bige-ops, remet donc les security groups dans le chemin entre les deux.
  • Internet : une VM sort directement avec une IP publique et un internet service, ou indirectement par un NAT service, avec une route 0.0.0.0/0 dans les deux cas.

Dans bige-ops, le layout (mono-VM, multi-VM, OKS) et les liens Visual ou YAML disent quoi exposer ; Outscale applique le comment. L’inventaire montre l’existant. Le détail ressource par ressource est sur Réseau avancé.

Garder un layout lisible

Multi-VM, LBU, security groups et pods : une config réseau grossit vite (ports orphelins, règles en double, variantes parallèles). L’assistant IA travaille avec ta propre clé API, en local : il lit la simulation, propose des corrections dans le respect des règles du projet et d’Outscale, et tu valides chaque changement.
