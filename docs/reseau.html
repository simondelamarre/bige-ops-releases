01 · Accès

Repérer l’entrée publique.

Repérer ce que les utilisateurs doivent pouvoir joindre : une application ou une API. Séparer les communications entre services et les accès aux données. Cette intention devient une topologie à configurer, avec des ressources identifiables et une seule lecture de leur rôle.

Besoins d’accès→Rôles public et privé

Public ne signifie pas sans authentification ; privé ne signifie pas sans risque.

02 · Topologie

Placer les ressources sur leurs réseaux.

Dans Visual et la configuration, relier les VM, services et données aux réseaux et sous-réseaux prévus. Les tables de routage, adresses publiques, NAT ou points d’entrée restent des ressources distinctes lorsque la cible les utilise. Leur relation doit représenter la configuration réelle.

Ressources déclarées→Zones et connexions

Les capacités et le vocabulaire diffèrent entre Outscale et OVHcloud ; la bêta conserve ces différences.

03 · Flux

Définir les connexions autorisées.

Relire les ports, règles et routes nécessaires au fonctionnement du produit. L’application peut joindre la base par le chemin interne prévu, sans ouvrir cette base à tout Internet. Appliquer la configuration puis examiner le plan permet de vérifier ce qui doit changer sur la cible.

Flux nécessaires→Règles à vérifier

Un trait dans Visual exprime une relation ; la règle et la portée générées doivent correspondre.

04 · Risque

Vérifier l’exposition d’un composant vulnérable.

Une CVE concerne un composant : son exposition aide à décider quoi examiner en priorité. Le parcours Vulnérabilités rapproche le service, les routes et les résultats du scan, en conservant les statuts public, privé ou inconnu. La correction reste liée à la version et au code concernés.

Contexte réseau→Priorité des alertes

Une CVE dans un service privé peut encore nécessiter une correction ; la topologie n’est pas un test d’exploitabilité.

Réseaux et sous-réseaux.

Placer les ressources selon les échanges attendus. Le sous-réseau ne suffit pas à lui seul à conclure : adresses, routes et règles d’accès déterminent le chemin réel.

Composer une simulation ↗

Entrée et sortie.

Une adresse publique ou un point d’entrée expose un service selon les règles associées. Un NAT sert à un accès sortant dans les topologies prévues ; il ne remplace pas une règle d’entrée.

Des règles relisibles.

Examiner protocoles, ports, sources et destinations dans la configuration produite. Le plan est une étape de lecture avant toute application au cloud.

Relire la configuration ↗

Vérifier l’exposition d’une faille.

Répondre avec des éléments, et garder « inconnu » lorsque le chemin ne peut pas être établi.

Le composant concerné.

Retrouver la version, le paquet ou l’image à l’origine de l’alerte. La présence du composant ne dit pas encore comment il est utilisé.

Le service et ses routes.

Rapprocher le composant du service et de l’exposition connue. Une route publique mérite un examen ; une route non détectée n’est pas une preuve d’absence d’accès.

L’action à prendre.

Corriger la version, ajuster une règle ou approfondir l’analyse selon le problème. La page Vulnérabilités détaille le triage et l’issue qui rassemble les éléments.

Questions fréquentes

Un service privé est-il automatiquement sécurisé ?

Le réseau limite les chemins d’accès. Il ne corrige pas le code, une dépendance vulnérable ou des permissions trop larges. Les règles réseau et le scan se complètent.

Visual modifie-t-il directement le cloud ?

La configuration de simulation est appliquée et générée dans le projet. Le plan et l’application au cloud restent des opérations distinctes : déplacer un objet ne vaut pas déploiement immédiat.

Pourquoi une exposition peut-elle être inconnue ?

Les informations accessibles peuvent ne pas suffire pour conclure sur une route ou son chemin réseau. Ce statut reste visible et appelle une vérification ; il n’est pas transformé en accès privé par défaut.

Ressources, réglages et détails techniques

Réseaux et exposition dépendent du fournisseur, de la topologie et des règles réellement générées.

Ce qu’on ouvre, ou pas

  • Face publique d’un layout VMs — selon la topologie, une adresse publique ou un LBU donne accès au service. Relire les ports et règles effectivement configurés.
  • VM data et bases — les topologies prises en charge permettent une zone privée pour les données. Relire l’adressage, le routage et les règles générées plutôt que déduire l’isolation du seul nom du subnet.
  • Pod OKS — Service selon le besoin ; réplicas ≠ exposition. L’accès à l’API Kubernetes dépend du CIDR administrateur configuré, notamment OKS_ADMIN_CIDR dans le parcours concerné.
  • SSH et deploy — sur la face app si nécessaire ; jamais sur une base « ouverte pour dépanner ».

Comprendre les ressources réseau Outscale

Le Net, les subnets, les routes, les security groups, les adresses publiques et les services Internet/NAT ont des rôles distincts. Leur combinaison détermine les chemins d’entrée et de sortie. Les paramètres exacts et les exceptions de filtrage doivent être relus dans la documentation du fournisseur et dans le plan généré.

Dans bige-ops, le layout (mono-VM, multi-VM, OKS) et les liens Visual ou YAML disent quoi exposer ; Outscale applique le comment. L’inventaire montre l’existant. Le détail ressource par ressource est sur Réseau avancé.

Garder un layout lisible

Multi-VM, LBU, security groups et pods : une config réseau grossit vite (ports orphelins, règles en double, variantes parallèles). L’assistant IA travaille avec la clé et le modèle sélectionnés : les outils lisent le projet local, et le contexte utile est envoyé au fournisseur API choisi si le modèle est distant. Examiner les propositions dans Visual et la configuration, puis relire le plan avant d’agir sur le cloud.
