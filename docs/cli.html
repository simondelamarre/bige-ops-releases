01 / PARTIR DU BON PROJET

Ouvrir le terminal dans le projet.

L’app utilise en priorité ses binaires bige-ops et oks-cli embarqués. Dans les réglages, retrouver leur chemin, leur version et les dépendances détectées. Le terminal s’ouvre dans le contexte de la simulation pour travailler sur les mêmes fichiers que l’interface.

Simulation ouverte→Projet et binaire identifiés

Les builds desktop livrent leur CLI ; son emplacement interne ne signifie pas qu’une commande globale est déjà installée dans tous les terminaux.

02 / VALIDER & GÉNÉRER

Générer les fichiers de la stack.

Valider le projet, puis générer les fichiers attendus par son mode de déploiement. Les erreurs doivent être traitées avant de poursuivre. La ligne de commande donne une autre entrée vers le travail du produit ; elle ne demande pas de reconstruire manuellement toute la configuration générée.

Configuration→Validation et génération

La génération prépare des fichiers. Elle n’applique pas les changements au cloud.

03 / LIRE LE PLAN

Examiner le plan avant de l’appliquer.

Lancer le plan de la cible sélectionnée et lire les ressources concernées. La commande, sa sortie et son code de retour rendent le résultat explicite. Un plan réussi prépare une décision : l’application au cloud ou le déploiement reste une opération distincte, lancée avec les accès nécessaires.

Fichiers générés→Plan de la cible

Un script qui exécute des mutations conserve ses responsabilités d’authentification, de portée et de confirmation.

04 / RETROUVER LE RÉSULTAT

Lire le résultat et les erreurs.

Consulter les états, les logs ou les résultats d’opération avec les commandes disponibles. L’interface reste le chemin principal pour lire et agir ; le terminal sert à approfondir, automatiser une séquence maîtrisée ou fournir un diagnostic précis. Les limites de chaque commande restent celles du produit.

Commande exécutée→État, sortie et logs

Toutes les fonctions desktop, notamment certains parcours de vulnérabilités, n’ont pas un équivalent CLI complet.

Utiliser les commandes livrées avec l’app.

Le desktop ne demande pas d’installer le projet Python source pour commencer.

CLI bige-ops embarqué

bige-ops et oks-cli sont livrés avec les builds desktop et recherchés en priorité. Le panneau Dépendances affiche leurs versions et les chemins retenus. Le CLI bige-ops porte les commandes de configuration et d’infrastructure ; oks-cli intervient dans les parcours Outscale Kubernetes.

Terminal et scripts

Les commandes exposées peuvent être lancées depuis un contexte de projet approprié. Certaines offrent des sorties JSON utiles aux intégrations. Il faut vérifier les arguments et les sorties de la commande choisie, sans supposer une parité totale entre toutes les vues desktop et la CLI.

MCP local

Le même binaire peut lancer le serveur MCP en stdio. Les agents externes utilisent des outils dédiés et limités, pas automatiquement toutes les commandes accessibles à l’utilisateur dans son terminal.

Vérifier les outils nécessaires.

Embarquer le moteur ne signifie pas embarquer tous les outils de l’écosystème.

Diagnostic de l’environnement

Le panneau Dépendances recherche les outils disponibles et leur version : Terraform, Docker et Compose, kubectl, kind, SSH, Git et les outils de cloud concernés. Le besoin dépend du parcours choisi.

Installation guidée

Pour les outils pris en charge, l’app peut lancer une installation ou une mise à jour, notamment par Homebrew ou un mécanisme de téléchargement prévu. Les logs et l’échec éventuel restent visibles. Certains outils demandent une installation manuelle.

Exécution locale

Tester une stack en conteneurs exige un environnement Docker opérationnel ; un binaire détecté ne suffit pas si le moteur n’est pas démarré. Kubernetes local et cloud ont également leurs prérequis propres.

Questions fréquentes

Faut-il installer Python pour utiliser l’app ?

Les builds desktop livrent le moteur CLI nécessaire à l’application ; l’utilisateur n’a pas à installer les sources Python pour ce parcours. Un environnement de développement depuis le dépôt a ses propres dépendances.

Tout fonctionne-t-il sans dépendances supplémentaires ?

Terraform, Docker, kubectl ou d’autres outils peuvent être nécessaires selon l’opération. L’app diagnostique l’environnement et guide l’installation des outils pris en charge. Le panneau Dépendances permet de vérifier les prérequis avant de lancer le parcours choisi.

Puis-je remplacer toute l’interface par des scripts ?

Les commandes disponibles couvrent de nombreux parcours d’infrastructure et d’exploitation. Certaines fonctions restent propres au desktop, notamment une partie de l’analyse de vulnérabilités et des éditeurs. Vérifier le périmètre de la commande avant de construire un automatisme.

Ressources, réglages et détails techniques

Les commandes doivent être lancées dans le contexte du bon projet. Le binaire embarqué, les outils installés et la connexion au fournisseur déterminent les capacités réellement disponibles.

Qui fait quoi

OutilRôleQuand
App desktop Composer, estimer, relire et déployer Chemin nominal
bige-ops validate / generate / plan / apply / deploy Sous l’app, ou script / CI / terminal
oks-cli Projet / cluster / nodepools / kubeconfig OKS Via apply --target oks (embarqué)
kubectl Appliquer / inspecter les manifests oks/apps/ Via deploy topologie oks, ou à la main

OKS en pratique

1. Simulation topologie oks (Visual ou bige-ops add stack oks). 2. generate → specs sous bige-ops/oks/ + apps YAML (réplicas, HPA, expose HTTP/TLS). 3. apply --target oks → oks-cli. 4. deploy → kubectl apply des Deployments (réplicas = pods).

Détail produit OKS : OKS & pods. Doc CLI complète : dans l’app (Docs) — pages cli/oks, cli/overview.

Terminal de l’app

Vrai shell PTY ($SHELL) : ls, git, bige-ops … dans le contexte fourni par l’app. Le chemin du binaire utilisé se vérifie dans les réglages. Les onglets restent actifs quand tu changes de vue.

Commandes utiles

bige-ops live status [--sample] [--oks]
bige-ops live sample --id i-xxxxxxxx
bige-ops pricing catalog-sync
bige-ops mcp                        # stdio pour un client MCP

Live = état lu par l’API Outscale + capacité Tina ; l’usage dans la VM (CPU, RAM, disque) s’obtient avec sample, par SSH. L’inventaire présente les états et les opérations disponibles, avec leur portée propre. Tarifs : sync du catalogue public Outscale par ReadPublicCatalog (page Tarifs dans l’app).

Bon à savoir

bige-ops génère et applique les manifests ; pour aller plus loin sur ton cluster, kubectl et ton kubeconfig sont à portée de main dans le terminal de l’app.

Outils embarqués et dépendances

bige-ops et oks-cli sont livrés avec le desktop. Terraform, Docker/Compose, kubectl, kind, SSH ou Git peuvent être nécessaires selon le parcours. Le panneau Dépendances les vérifie et propose une installation pour les outils pris en charge. Exécuter une stack locale demande notamment un moteur Docker démarré.
