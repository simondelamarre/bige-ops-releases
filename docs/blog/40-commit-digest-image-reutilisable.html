Du commit au digest, l’image garde son identité

Bige Ops relie la branche, le commit et le digest GHCR pour réutiliser une image déjà construite et rendre chaque déploiement plus facile à relire.

Le commit fixe le code

Une branche est pratique pour travailler. Son nom reste lisible, son contenu évolue et l’équipe peut la fusionner ou la supprimer. Cette souplesse en fait un bon point de départ pour choisir une version à déployer, mais une branche seule ne suffit pas à décrire durablement le résultat.

Le commit apporte cette précision. Son identifiant désigne un état déterminé du dépôt : les mêmes fichiers, le même Dockerfile et le même contexte de build. Bige Ops résout donc la branche choisie vers son commit avant de chercher ou de construire une image.

La branche conserve le sens de la décision. Le commit conserve l’état du code. Les deux informations se complètent dans l’historique.

Le digest fixe l’image

Une image Docker possède souvent un tag comme latest, main ou un numéro de version. Ces noms sont utiles pour les humains et pour les workflows, mais un tag peut être déplacé vers une autre image.

Le digest identifie le contenu publié dans le registre. Une référence comme ghcr.io/org/app@sha256:… désigne l’artefact exact que la cible doit récupérer. Le déploiement ne dépend plus de ce que le tag latest représentera demain.

Bige Ops utilise cette référence précise lorsqu’une image GHCR correspond au commit demandé. Le fichier Compose de surcharge transmis à la VM remplace uniquement l’image du service concerné. La configuration runtime, les volumes et les autres services restent dans leur périmètre.

Le tag garde un rôle humain

Les tags restent utiles. Un workflow peut publier main, v1.4.0 et le hash court du commit vers le même artefact. Une personne retrouve alors facilement une version dans GitHub Packages, tandis que le déploiement conserve le digest pour l’exécution.

Cette organisation évite de demander à un seul nom de remplir trois rôles. La branche porte l’intention de travail. Le commit porte l’état source. Le digest porte l’image réellement exécutée. Un tag d’image apporte un repère supplémentaire, mais il ne remplace pas les trois autres dans la preuve du déploiement.

Le build reste une décision

Reconstruire une image a un coût. La CI réinstalle les dépendances, compile le projet, lance ses contrôles, scanne l’artefact et le transfère vers le registre. Cette dépense est justifiée lorsqu’un nouveau commit arrive ou lorsque la politique de l’équipe impose une reconstruction contrôlée.

Elle apporte peu lorsqu’une image du commit existe déjà et que son digest est disponible. Bige Ops cherche donc cet artefact exact avant de proposer un nouveau build dans le parcours GHCR. S’il le trouve, il le réutilise. S’il manque, le workflow de build du service garde son rôle.

Cette règle reste prudente. Une image proche, un ancien latest ou le paquet d’une autre branche ne remplacent pas l’artefact attendu. Réutiliser signifie retrouver une identité vérifiable, pas choisir le fichier qui ressemble le plus au besoin.

GHCR conserve le résultat

GitHub Actions construit l’image ; GHCR la stocke. Le registre ne devine pas la branche à livrer et ne construit rien à la place du workflow. Il expose les manifests et les blobs que les comptes autorisés peuvent lire.

Pour un package privé, l’accès au dépôt Git ne donne pas automatiquement accès à l’image. La connexion utilisée par Bige Ops doit aussi autoriser la lecture des packages. Le préflight vérifie ce point avant de lancer le déploiement et guide la reconnexion lorsque ce droit manque.

Une fois l’accès établi, la VM récupère le digest sélectionné. Le registre devient ainsi le lien entre une CI qui produit et une cible qui exécute, avec une identité commune entre les deux étapes.

La cible reçoit une référence précise

Sur la VM, Bige Ops place la surcharge d’image à côté des fichiers Compose runtime effectivement utilisés par la stack. Le script de déploiement peut alors combiner la configuration principale et cette référence sans chercher un fichier dans un ancien répertoire de build.

Ce détail de chemin paraît modeste. Il sépare pourtant deux responsabilités : les sources qui ont servi à construire et les fichiers qui servent à exécuter. Une image GHCR déjà publiée ne nécessite pas de recopier tout le dépôt applicatif pour être lancée.

Le service repart avec ses variables runtime et son environnement configuré. Les secrets de build restent dans le parcours de build ; les secrets d’exécution restent dans le coffre et sur la cible. Le digest ne transporte ni l’un ni l’autre dans son nom.

Le rollback suit la même règle

Un rollback utile remet une image connue, pas une branche supposée identique. Bige Ops conserve l’image saine courante et la précédente dans son historique opérationnel local. La confirmation affiche le service, la date, la référence Git, le commit et l’image concernée.

Pour une image GHCR, le digest reste récupérable sur une autre VM disposant des droits adaptés. Pour une image construite uniquement sur une VM, la réutilisation dépend de sa présence sur cette cible. Les deux chemins restent possibles, avec des propriétés différentes que l’interface doit expliquer.

La même idée traverse tout le parcours : garder un nom lisible pour choisir, une identité source pour comprendre et une identité d’artefact pour exécuter. C’est ce lien qui rend un déploiement reproductible et son histoire relisible.
