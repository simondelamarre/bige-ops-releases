Pods, nodes et nodepools : comprendre le coût

Sur Kubernetes, la facture suit surtout les VM des nodepools. Les pods utilisent cette capacité et déclenchent un nouveau palier lorsqu'elle devient insuffisante.

La facture suit surtout les machines

Sur un cluster Kubernetes hébergé sur des VM, le cloud facture d'abord les machines, leurs disques et les ressources réseau. Le nodepool regroupe des machines comparables. Les pods utilisent cette capacité déjà provisionnée.

Un pod ou dix pods peuvent donc conserver le même coût d'infrastructure lorsqu'ils tiennent sur les mêmes nodes. La facture change quand le cluster ajoute une VM, attache un volume, crée un load balancer, transfère davantage de données ou conserve plus de logs.

Cette lecture concerne un Kubernetes classique dont les workers sont des VM. Les offres serverless et certains services de conteneurs utilisent d'autres unités de facturation.

    N1 --> S{Un 7e replica arrive}

Le prix avance par paliers

Kubernetes planifie les pods à partir de leurs requests CPU et mémoire, de la capacité encore disponible et de contraintes comme les zones, l'affinité, les volumes ou le nombre maximal de pods par nœud. La documentation Kubernetes sur les requests et limits explique que le scheduler utilise les requests pour décider si un pod peut tenir sur un nœud.

Une première approximation ressemble à ceci :

capacité par node = minimum de :
  CPU utilisable / request CPU d'un replica
  RAM utilisable / request RAM d'un replica
  limites de pods, d'adresses IP et de volumes

nodes requis = replicas / capacité par node, arrondi au-dessus

La réserve du système, les DaemonSets et la marge de panne réduisent la capacité brute. Une règle d'anti-affinité peut aussi demander deux nodes alors que le CPU et la mémoire tiendraient sur un seul.

Prenons un exemple simple : un node accueille six replicas après réserve. Les six premiers utilisent la VM en place. Le septième peut déclencher une seconde VM et ouvrir un nouveau palier de coût pour tout le nodepool.

Requests, usage et facture mesurent trois réalités

Une interface d'optimisation doit conserver trois mesures séparées :

  • requests : capacité réservée pour la planification ;
  • usage réel : CPU et mémoire effectivement consommés ;
  • facture : machines et services réellement provisionnés pendant une durée.

Un workload peut demander 2 vCPU et en utiliser 0,2. Le scheduler réserve pourtant les 2 vCPU et peut déclencher l'ajout d'un node. Des requests très basses remplissent davantage le node, avec plus de risque de contention ou d'éviction.

Le right-sizing s'appuie donc sur une période représentative, les pointes, les redémarrages, la saisonnalité et la marge souhaitée en cas de perte d'un node.

L'allocation répartit le coût du nodepool

Une équipe peut répartir le prix du nodepool entre les workloads selon les requests, l'usage ou une combinaison des deux. Cette allocation aide à repérer un namespace surdimensionné ou une application qui occupe une part importante d'un pool GPU.

Cette valeur reste une convention de pilotage. Si un pod disparaît et que la VM reste allumée, la facture de la VM continue. L'économie apparaît lorsque la capacité libérée permet de retirer un node ou d'éviter son ajout futur.

Des outils comme OpenCost proposent une allocation par cluster, namespace ou workload. Le catalogue et la consommation du fournisseur cloud restent les sources du montant facturé.

Certains pods ajoutent des ressources facturées

Le nombre de pods peut entraîner d'autres ressources :

  • un volume persistant par replica ;
  • un load balancer créé pour un Service ;
  • des adresses IP ou un NAT ;
  • davantage de trafic sortant ;
  • des snapshots et sauvegardes ;
  • une hausse des logs, métriques et traces conservés ;
  • un registre d'images ou des scans supplémentaires.

Une base en StatefulSet avec un volume par pod suit donc une courbe différente d'une API stateless dont les replicas partagent seulement les nodes.

Le control plane complète l'estimation

Dans un service managé, le control plane peut être gratuit, inclus ou facturé selon le fournisseur et le profil choisi. Dans un Kubernetes self-managed, l'estimation ajoute les masters, leurs disques, le load balancer de l'API, les sauvegardes etcd et l'exploitation.

L'estimation complète devient donc :

control plane
+ workers minimum / attendus / maximum
+ disques des nodes et volumes applicatifs
+ ingress, load balancers, IP et NAT
+ snapshots, logs et trafic
+ charge d'exploitation, affichée séparément

Le coût complet permet de comparer les deux modes avec le même niveau de service, plutôt qu'avec le seul prix des workers.

L'interface explique le prochain palier

Pour chaque nodepool, la conception de l'interface Bige Ops retient :

  • le nombre minimum, actuel et maximum de nodes ;
  • la capacité réservée et l'usage observé ;
  • la marge si un node disparaît ;
  • le nombre de replicas supplémentaires encore disponibles ;
  • le prix du prochain node ;
  • les workloads qui occupent la capacité ;
  • les coûts inconnus, affichés comme tels.

La formulation relie usage et facture : « ce workload utilise 38 % de la capacité réservée ; quatre replicas supplémentaires tiennent avant l'ajout d'une VM estimée à 46 euros par mois ». Le lecteur voit ainsi le palier qui change vraiment le coût.

Le calcul Bige Ops reste en conception

Bige Ops sait déjà estimer des VM, des disques et plusieurs ressources cloud. Le produit modélise aussi des nodepools et suit des workloads. Le calcul complet de capacité Kubernetes reste en conception.

La prochaine étape fixe la réserve système, les contraintes de placement, le traitement des inconnues, le modèle d'autoscaling et la marge de panne. Le résultat prendra la forme d'une fourchette minimum / attendue / maximum, complétée par le prochain seuil de coût.

Ce contrat sera ensuite rapproché des mesures Live et de la consommation du fournisseur, puis validé sur des clusters réels avant d'être présenté comme une capacité stabilisée.
