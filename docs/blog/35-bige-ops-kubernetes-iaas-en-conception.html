Bige Ops prépare Kubernetes sur votre IaaS

Bige Ops part de la stack applicative

Une personne arrive avec une application, une base, quelques services et un budget. Bige Ops traduit cette stack en options d'infrastructure compréhensibles, avant d'exposer les détails du control plane, des nodepools, du réseau et du stockage.

Bige Ops part de cette stack et compare trois chemins :

  1. une VM ou un groupe de VM ;
  2. le Kubernetes managé du fournisseur ;
  3. un Kubernetes opéré par Bige Ops sur les VM du compte IaaS.

Chaque chemin garde sa place. Une petite application stable peut tenir sur une VM. Kubernetes managé convient à une équipe qui souhaite déléguer une partie du control plane. Kubernetes sur IaaS apporte davantage de contrôle lorsque ce bénéfice compense les responsabilités d'exploitation.

La recommandation expose les compromis

La carte de décision montre les faits utilisés :

  • nombre de services et besoin de les scaler séparément ;
  • fréquence des déploiements et besoin de rolling update ;
  • disponibilité attendue ;
  • charge stable ou saisonnière ;
  • CPU, mémoire et GPU ;
  • bases et volumes persistants ;
  • compétence d'exploitation disponible ;
  • coût mensuel minimum, attendu et maximum.

Plusieurs services stateless, des déploiements fréquents, des pools GPU et un besoin d'auto-healing rendent Kubernetes pertinent. Une seule API, une base et une charge prévisible peuvent rester plus simples sur une VM. Une production hautement disponible avec peu de capacité d'exploitation peut justifier le Kubernetes managé plutôt que le self-managed.

L'interface explique ce que chaque option prend en charge, ce qu'elle laisse à l'équipe et le niveau de service obtenu. La recommandation choisit une option pour la stack étudiée, avec ses raisons et ses limites.

Visual montre cinq objets simples

La configuration reste lisible en regroupant les pods sous un workload et son nombre de replicas. Les pods réels apparaissent ensuite dans Live, les logs et le diagnostic.

Le canvas s'organise autour de cinq groupes :

  • Cluster : mode managé ou Bige Ops, version, disponibilité et coût fixe ;
  • Nodepool : type de VM, zones, minimum, cible, maximum, prix et workloads ;
  • Workload : image, replicas, requests/limits, placement et exposition ;
  • Données : service managé, VM privée ou StatefulSet ;
  • Accès : API Kubernetes, ingress public et flux privés.

Les notions plus techniques restent disponibles dans une section avancée. L'interface principale répond d'abord à des questions concrètes : combien de machines, quels services tournent dessus, qu'est-ce qui est public, où sont les données et combien coûte le prochain palier ?

Chaque action garde une portée claire

Une action simple affiche sa cible, son effet et ses dépendances.

  • Appliquer crée ou modifie l'infrastructure après revue du plan.
  • Ajuster la capacité agit sur un nodepool précis.
  • Déployer agit sur un workload et une image identifiés.
  • Mettre à niveau ordonne control plane, workers et add-ons.
  • Réparer part d'un diagnostic et propose une mutation ciblée.
  • Sauvegarder distingue etcd des données applicatives.
  • Détruire inventorie d'abord volumes, IP, load balancers et sauvegardes.

Avant confirmation, chaque action doit montrer les dépendances, l'interruption possible, la variation de coût, les commandes prévues et la manière de reprendre un échec.

L'agent explique, le moteur calcule

Un modèle de langage lit un dépôt, reformule un besoin et explique un compromis. Les tarifs, les CIDR et la capacité des nodepools restent calculés et validés par les moteurs déterministes de Bige Ops.

Le parcours Bige Ops sépare plusieurs capacités :

Capacité Rôle
Conseiller d'architecture Comparer VM, managed et Bige Ops, puis demander les informations manquantes
Analyseur de capacité Calculer placement, nodes requis, marge et prochain seuil de coût
Planificateur Kubernetes Produire les étapes ordonnancées, leurs risques et leurs reprises
Conseiller données Comparer base managée, VM privée et base dans Kubernetes
Conseiller coût Relier catalogue provider, durée et capacité minimum/attendue/maximum
Opérateur jour 2 Diagnostiquer puis proposer scale, upgrade, remplacement ou restauration

Ces skills utilisent des outils Bige Ops structurés. Les formules, validations provider et mutations restent dans le CLI et les moteurs du produit. L'agent ouvert depuis l'interface reçoit le contexte courant, propose, puis laisse la confirmation humaine déclencher l'action.

La base garde plusieurs options

PostgreSQL, MongoDB ou Redis peuvent rester sur une VM privée de la même infrastructure. Cette option sépare le cycle de vie des données de celui du cluster.

Dans ce cas, les workers et la VM de données partagent un réseau routable ou un peering. Le security group de la base autorise uniquement son port depuis les workers. Le CNI détermine si la base voit l'IP du pod ou celle du node après SNAT. Une NetworkPolicy limite aussi les workloads autorisés à sortir vers la base. Un DNS privé stable évite d'inscrire une adresse physique dans l'application.

flowchart TB
    I[Ingress public] --> W[Workload Kubernetes]
    subgraph K[Cluster sur réseau privé]
      W --> N[Workers du nodepool]
    end
    N -->|Port DB autorisé| D[(Base sur VM privée)]
    X[Autre workload] -. Refus NetworkPolicy .-> D
    D --> O[Sauvegarde objet hors cluster]

Une base placée dans Kubernetes exige davantage : StatefulSet ou opérateur mature, CSI, volumes persistants, anti-affinité, budget de disruption et sauvegarde hors du cluster. Elle utilise en général un nodepool data dédié au lieu de partager par défaut les workers stateless.

Le choix doit apparaître dans Visual en langage utilisateur : service managé, VM privée ou dans le cluster, avec la raison, le niveau de résilience, le coût et la sauvegarde attendue.

L'implémentation avance par preuves

L'implémentation avance par lots :

  1. modèle canonique et frontière de responsabilité ;
  2. conseiller en lecture seule capable de refuser Kubernetes ;
  3. calcul de capacité et estimation par paliers ;
  4. parcours Visual et actions scopées ;
  5. premier provider et cluster de démonstration ;
  6. base privée puis profil stateful dans Kubernetes ;
  7. upgrades, certificats, sauvegarde etcd et remplacement de nœuds ;
  8. validation réelle et comparaison de facture.

Le premier prototype couvre un cluster, un provider et les opérations essentielles. Le multi-cluster, le multi-région actif-actif, Windows, le service mesh et l'air-gap complet restent hors de ce premier périmètre.

La fonction reste en conception

Bige Ops dispose déjà de briques concrètes : simulations, Terraform, test Kubernetes local, déploiement de workloads, nodepools OKS, logs, métriques et estimation de VM. Le nouveau sujet consiste à les relier dans une expérience cohérente et à assumer le cycle de vie du cluster.

Plusieurs choix structurent encore le produit : distribution Kubernetes, moteur de bootstrap, contrôleurs provider, stockage, source de vérité et composant permanent lorsque l'app est fermée. Nous les prototypons avant de fixer le contrat public.

Le mode Kubernetes sur IaaS reste donc en conception dans Bige Ops. La création du cluster constitue la première preuve. La disponibilité passe aussi par le scale, la mise à niveau, la panne d'un master, la restauration, la sécurité du réseau privé et le nettoyage des ressources facturables.
