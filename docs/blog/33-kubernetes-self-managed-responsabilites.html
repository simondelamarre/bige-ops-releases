Kubernetes self-managed : vos responsabilités d'exploitation

Sur Kubernetes self-managed, l'équipe opère les VM, le control plane, etcd, le réseau, le stockage et les reprises. Voici le contrat complet.

Kubernetes repose sur des machines et des commandes

Un cluster Kubernetes assemble des machines, un réseau, des certificats et des logiciels connus. Un plan bien ordonné crée les VM, installe le runtime de conteneurs, initialise le premier master, joint les autres nœuds, installe le réseau du cluster puis déploie les applications.

Cette installation s'automatise très bien. Des commandes CLI et shell forment un moteur fiable quand chaque étape possède des préconditions, un résultat contrôlable, un délai maximal et une stratégie de reprise.

Le cycle de vie continue ensuite. Un service Kubernetes managé prend en charge une partie du control plane et de son exploitation. Avec un cluster self-managed, l'équipe récupère cette responsabilité. Le choix porte donc autant sur le niveau de service attendu que sur la création des VM.

Le contrat continue après l'installation

Le jour 0 couvre la création : machines, réseau, paquets, cluster, nodepools et premier déploiement. Le jour 2 couvre la vie du cluster : correctifs, certificats, changements de version, saturation, panne d'un master, perte d'un disque et restauration.

La documentation Kubernetes sur les composants d'un cluster distingue clairement le control plane des nœuds qui exécutent les applications. La documentation de haute disponibilité avec kubeadm ajoute notamment le load balancer de l'API et plusieurs nœuds de contrôle.

Le control plane porte la disponibilité

Un master unique convient à l'apprentissage et aux environnements éphémères. Une production hautement disponible utilise généralement plusieurs masters. L'exploitation couvre alors le quorum etcd, la distribution de l'accès API et le remplacement progressif d'un membre défaillant.

Une sauvegarde etcd devient utile quand sa restauration est testée. La documentation etcd décrit une opération explicite qui recrée un cluster logique à partir d'un snapshot. Le test vérifie ensuite les objets, les secrets, les volumes et le redémarrage des workloads.

Les certificats suivent le même principe. Leur renouvellement, l'ajout d'un master et la révocation d'un accès administrateur font partie du contrat d'exploitation.

Les nodepools demandent un contrôleur actif

Un nodepool regroupe des nœuds comparables : même type de VM, mêmes labels, contraintes de zones et politique de scaling. Bige Ops peut ajouter des VM pendant une opération demandée par l'utilisateur. Le scaling automatique demande en plus un composant actif lorsque l'application desktop est fermée.

Le cluster autoscaler, ou un contrôleur équivalent, observe les pods en attente, appelle l'API IaaS, attend le nouveau nœud puis le retire avec les précautions de disponibilité. Ses credentials cloud restent limités, rotatifs et auditables.

La même frontière existe pour les autres ressources :

  • un Service de type LoadBalancer suppose un cloud-controller compatible ou une opération Bige Ops qui crée et maintient le load balancer ;
  • un volume dynamique s'appuie sur un pilote CSI compatible ;
  • le DNS privé, l'ingress et les certificats possèdent chacun leur contrôleur ou leur plan d'exécution ;
  • l'auto-healing des nœuds a besoin d'un contrôleur disponible en continu.

Le coût dépend du niveau de service

Un control plane managé peut apparaître comme une ligne dédiée dans la facture. Le coût self-managed regroupe de son côté les masters, leurs disques, le load balancer de l'API, les sauvegardes et le temps d'exploitation.

Le self-managed devient pertinent quand il apporte un bénéfice identifié : contrôle de la distribution, portabilité, intégration particulière, absence d'offre managée adaptée ou compétence plateforme déjà disponible. Une petite application stable peut rester sur une ou quelques VM. Une équipe qui souhaite une haute disponibilité avec moins d'exploitation du control plane peut retenir le service managé.

Bige Ops compare ces options avec les mêmes axes : prix, disponibilité, compétences, données et responsabilités. Le choix dépend de la stack et du niveau de service attendu.

La piste Bige Ops reste en conception

Bige Ops sait déjà modéliser des clusters et des nodepools, générer des workloads Kubernetes, tester une stack localement, déployer des services ciblés et piloter le parcours OKS d'Outscale. Ces briques valident une partie de l'ordonnancement.

Le mode Kubernetes opéré avec Bige Ops sur des VM IaaS reste en conception. La distribution, le moteur de cycle de vie, les contrôleurs permanents, le premier provider et le niveau de support restent à prototyper puis à valider.

Le travail avance dans cet ordre : comparer VM, Kubernetes managé et self-managed ; rendre le coût et les responsabilités visibles ; prototyper sur un provider ; puis prouver la mise à niveau, la panne, la restauration et le nettoyage. L'interface proposera ce mode après validation de ce contrat d'exploitation.
