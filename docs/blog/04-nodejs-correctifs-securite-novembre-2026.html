Node.js 22, 24 et 26 : les correctifs de sécurité sont disponibles

Node.js 22.23.5, 24.22.3 et 26.13.1 corrigent des failles HTTP/2, HTTPS, TLS et mTLS, dont plusieurs de sévérité High.

Ce qui a été publié le 11 novembre

Le projet Node.js a publié trois versions de sécurité pour ses lignes LTS actives : 22.23.5, 24.22.3 et 26.13.1. L’avis préalable est donc devenu une liste de correctifs vérifiables. Le niveau maximal annoncé reste High.

Les mises à jour embarquent aussi de nouvelles versions de dépendances : llhttp sur les trois lignes, undici sur Node.js 24 et 26, ainsi que SQLite sur Node.js 22 et 24.

Ligne maintenue Version corrigée
Node.js 22 LTS 22.23.5
Node.js 24 LTS 24.22.3
Node.js 26 LTS 26.13.1

Les branches en fin de vie ne reçoivent pas ces versions. Les maintenir en production laisse donc un problème distinct du simple redéploiement de l’application.

Pourquoi ces correctifs comptent

Plusieurs défauts sont exploitables à distance sans authentification sur des serveurs qui utilisent les chemins concernés : arrêt du processus HTTP/2, fuite de mémoire ou de descripteurs, lecture de mémoire lors d’échanges HTTPS, ou corruption liée à la fermeture d’un stream.

La publication corrige aussi des contournements de politiques TLS et mTLS liés au SNI et à la reprise de session. Un autre défaut pouvait faire apparaître des identifiants de proxy dans des erreurs, puis dans stderr, les logs de conteneur ou un service de collecte.

Toutes les applications Node.js ne sont pas exposées de la même façon. Il faut relier la version réellement exécutée aux fonctions utilisées : HTTP/2, respondWithFile(), callbacks TLS, contextes SNI, mTLS, proxy ou modèle de permissions.

Mettre à jour le runtime réellement exécuté

La version de package.json ne décrit pas toujours le runtime de production. Node.js peut venir d’une image Docker, d’une VM, d’un runner CI, d’un worker ou d’un outil embarqué.

  1. Relever node --version dans chaque environnement qui exécute ou construit le service.
  2. Mettre à jour l’image de base, le gestionnaire de versions ou le runner vers la version corrigée de la même ligne LTS.
  3. Reconstruire l’artefact : redémarrer un ancien conteneur ne change pas son runtime.
  4. Tester les routes HTTP/HTTPS, les connexions longues, les transferts et les politiques de certificat utilisées.
  5. Redéployer le seul service concerné, puis vérifier de nouveau node --version dans le conteneur ou sur la VM cible.

Un reverse proxy limite parfois l’accès direct à HTTP/2 ou TLS dans Node.js, mais il ne prouve pas que tous les chemins vulnérables sont inaccessibles. L’inventaire et la configuration effective restent nécessaires.
