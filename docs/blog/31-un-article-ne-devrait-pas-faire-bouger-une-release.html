Un article ne devrait pas faire bouger une release produit

Une release doit rester une preuve

Une release produit ne devrait pas être seulement un numéro et trois fichiers à télécharger. Elle devrait relier un état précis du code, des contrôles réussis, des artefacts reproductibles et une décision de publication. Son tag doit rester immuable. Son résultat doit être attestable. Son statut doit être vert.

Une correction éditoriale obéit à un autre rythme. Une faute dans un article, une source à mettre à jour ou un titre à reprendre ne justifient ni de reconstruire l’application desktop, ni de créer une version artificielle, ni de modifier la preuve associée à des binaires déjà publiés.

Dans Bige Ops, ces deux niveaux sont encore trop proches. Le blog n’est pas embarqué dans les binaires, mais sa source, son générateur, son déploiement et les releases publiques partagent des dépôts, des branches et un credential. Le problème n’est donc pas que « du Markdown serait une release ». Le problème est que le contenu éditorial et la distribution du produit empruntent une même zone de confiance.

Ce que fait réellement le dépôt aujourd’hui

Les articles sources vivent dans packaging/releases-repo/blog/, au sein du dépôt privé du produit. Un script Node transforme chaque Markdown en page HTML avec marked. Le même build régénère la liste des articles, les métadonnées, le sitemap et l’index de recherche local.

La publication automatique passe par le workflow Sync landing. Il se déclenche lorsqu’un changement du site, du blog ou de son générateur arrive sur main. Il installe les dépendances, exécute build:site, lance check_site.py, clone ensuite le dépôt public bige-ops-releases, remplace son dossier docs/, puis pousse le résultat. GitHub Pages sert ce dossier sur bige.dev.

Les binaires suivent un autre workflow, Release desktop, déclenché par un tag v*. Il construit le DMG macOS, l’AppImage et le paquet Debian, les dépose dans une release publique, génère latest.json, puis rend la release visible.

Les deux workflows sont distincts, mais ils écrivent dans le même dépôt public et utilisent le même secret RELEASES_GITHUB_TOKEN. Ce dépôt porte donc à la fois une branche mutable pour GitHub Pages et des tags et assets qui doivent représenter des versions immuables du produit.

Il existe enfin une deuxième route éditoriale : scripts/sync-releases-landing.sh. Elle peut copier l’arbre docs/ local vers le dépôt public sans attendre un tag ni même un passage du contenu par main. C’est ainsi que la veille du 12 novembre a été publiée : le commit source des articles 28 et 29 est encore seulement sur develop, tandis que le dépôt public contient un commit de synchronisation séparé.

Cette route manuelle évite de fabriquer une release produit pour un article. Elle crée toutefois une autre difficulté : la provenance publique ne désigne plus directement un commit publié de main, mais l’état généré présent sur la machine au moment de la synchronisation.

« La release devrait être verte » : elle ne l’est pas

Au 14 novembre 2026, le dernier workflow Release desktop de Bige Ops, celui de v0.13.1, est marqué en échec par GitHub Actions. Ses jobs macOS et Linux ont pourtant réussi. Les trois binaires ont été téléversés. latest.json est présent et la release publique a été publiée.

Le suivi du projet documente la cause opérationnelle : GitHub a clos le run alors que le job final publish était encore en attente, sans étape exécutée ni runner. Les opérations finales, conçues pour être idempotentes, ont ensuite été lancées manuellement. GitHub refuse par ailleurs de relancer les seuls jobs en échec puisqu’aucun job exécuté n’apparaît comme fautif.

Le produit est donc disponible, les contrôles Quality de main et develop sont verts, et la dernière synchronisation de la page publique est verte. Mais la preuve principale de publication de v0.13.1 reste rouge.

Cette divergence ne vient pas des articles Markdown. Elle montre pourquoi il faut éviter de demander à une seule notion de « release » de raconter à la fois la qualité du code, la publication des binaires et l’état du site. Quand ces attestations se recouvrent, une équipe peut être tentée de créer un nouveau tag seulement pour retrouver un voyant vert. Ce nouveau numéro ne corrigerait pas la preuve précédente; il ajouterait une version produit sans changement produit.

Les risques concrets du couplage actuel

Un rayon d’action trop large

Le secret qui permet au workflow du site de pousser docs/ est aussi celui que le workflow desktop utilise pour créer une release et téléverser ses assets. Un défaut du générateur, une dépendance compromise ou un détournement du chemin éditorial se trouve ainsi dans la même zone d’autorité que la distribution des binaires.

Les permissions déclarées par les workflows sur le dépôt privé restent en lecture seule. Le pouvoir supplémentaire vient du token externe confié aux jobs. Séparer les fichiers sans séparer les identités ne réduit donc pas entièrement le rayon d’action.

Deux provenances qui ne racontent pas la même chose

La route automatique relie la page publique à un commit de main. La route manuelle crée un commit générique dans le dépôt public à partir d’un arbre local généré. Les deux sont traçables, mais pas avec la même précision.

Pour revenir en arrière, faut-il restaurer un commit du site, un commit du dépôt produit, un tag ou les trois ? Pour auditer une date donnée, quel état du Markdown a produit l’HTML servi ? La réponse existe dans l’historique et les notes d’exploitation, mais elle n’est pas portée par un manifeste unique et vérifiable.

Le GitFlow produit devient une contrainte éditoriale

Le workflow automatique du site n’exige pas de tag : un push sur main suffit. En revanche, la procédure normale de Bige Ops réserve main aux états de production et y arrive par une release ou un hotfix GitFlow. Si cette convention est appliquée strictement au blog, une correction d’article attend la prochaine release ou pousse à créer une version produit sans raison fonctionnelle.

La synchronisation manuelle contourne ce problème, mais elle contourne aussi le chemin develop → main qui sert normalement de preuve publiée. Les deux options sont insatisfaisantes : tag churn d’un côté, provenance moins forte de l’autre.

Le contrôle du site arrive tard

Le workflow général Quality, exécuté sur les pull requests, develop et main, teste Python, le desktop et Rust. Il ne construit pas le site. Le build et check_site.py s’exécutent dans Sync landing, après l’arrivée sur main, juste avant l’écriture dans le dépôt public.

Le script de vérification contrôle la structure HTML, les liens, les ancres, les assets et les pages orphelines. Il ne constitue pas une politique de sécurité du contenu. Le générateur insère dans la page le HTML produit par marked, et aucune étape de sanitization n’est visible dans la chaîne actuelle. Cela ne signifie pas qu’un visiteur peut injecter du code : les auteurs du dépôt sont la frontière de confiance. Cela signifie qu’un compte de contribution compromis ou une automatisation mal cadrée pourrait introduire du HTML actif que le contrôle de liens ne refuserait pas.

Mutable et immuable partagent le même nom

Une page web est, par nature, corrigée et remplacée. Une release et ses artefacts devraient, à l’inverse, rester associés au tag qui les a produits. Les héberger dans le même dépôt public n’altère pas automatiquement les binaires, mais mélange les journaux, les droits et les opérations de retour arrière. L’interface GitHub montre alors côte à côte une branche de contenu qui bouge et des versions qui ne devraient plus bouger.

La contrainte n’est pas seulement visuelle. La release publique v0.13.1 n’est pas déclarée immuable par GitHub, et les commandes de publication utilisent gh release upload --clobber pour permettre une reprise idempotente. Ce choix a une utilité opérationnelle, mais il autorise le credential de publication à remplacer un asset sous le même tag. Les digests publiés permettent de constater une différence; aucun manifeste signé ou mécanisme d’attestation ne la bloque aujourd’hui. Rien n’indique qu’un binaire a été remplacé : le risque vient de la capacité laissée ouverte.

Séparer les preuves avant de séparer les outils

La première correction n’est pas nécessairement une migration spectaculaire. Il faut d’abord nommer trois états indépendants :

  1. Qualité produit : tests du code source sur un commit précis.
  2. Release binaire : build, digests, notes et publication depuis un tag précis.
  3. Publication éditoriale : source Markdown revue, HTML validé et déployé depuis un commit de contenu précis.

Chacun devrait avoir son propre statut vert, son identité d’écriture et sa procédure de rollback. Un échec de publication du site ne devrait pas rendre ambiguë une release binaire. Une release rouge ne devrait pas être repeinte par un article ni par un nouveau numéro sans changement produit.

Une évolution possible serait de placer le contenu dans un dépôt ou, au minimum, une branche protégée et un pipeline dédiés. Le Markdown y serait validé avant fusion, le HTML strictement filtré, puis publié avec une identité limitée à Pages. Un manifeste pourrait enregistrer le commit source, les versions du générateur et des dépendances, ainsi que les empreintes des fichiers produits. La signature ou l’attestation de cet artefact renforcerait encore la provenance.

Bige Ops pourrait ensuite référencer explicitement une version de contenu ou simplement pointer vers le site publié, sans transformer chaque article en version de l’application. Cette architecture n’est pas décidée aujourd’hui. Elle décrit la conséquence logique du diagnostic : le produit et l’éditorial peuvent se parler sans partager la même autorité de publication.

La cible : trois voyants verts, pas un seul voyant ambigu

Une chaîne de release fiable ne consiste pas à obtenir coûte que coûte une coche verte. Elle consiste à pouvoir expliquer quelle preuve est verte, pour quel objet, à partir de quelle source et sous quelle identité.

Pour Bige Ops, la prochaine étape utile est donc de découpler l’article, la page et le binaire dans les contrôles comme dans les droits. Le blog doit pouvoir être corrigé sans nouveau tag produit. La release doit pouvoir rester immuable sans bloquer l’éditorial. Et lorsqu’un workflow de publication est rouge, son état ne doit pas être masqué par le fait que les fichiers sont quand même arrivés à destination.
