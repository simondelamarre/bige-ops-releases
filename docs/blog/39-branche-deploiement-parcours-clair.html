Déployer reste un geste produit

Une équipe veut mettre une version en ligne. Elle connaît son dépôt, la branche à livrer et les services concernés. Son besoin tient en une phrase : choisir cette branche, lancer le déploiement et suivre le résultat.

L’infrastructure ajoute pourtant plusieurs réalités. Il faut retrouver la bonne cible, savoir où construire l’image, transmettre la configuration d’exécution et vérifier que le service repart. Chacune compte. Aucune ne devrait obliger à chercher l’action principale au milieu de tout l’inventaire cloud.

Bige Ops 0.15 ajoute donc un espace Déploiements. Inventory et Visual conservent leurs actions rapides, utiles lorsqu’on travaille déjà sur une ressource. La nouvelle vue part du geste quotidien : une branche, un ou plusieurs services, puis une exécution visible dans l’historique.

La branche exprime une intention

Une branche Git raconte un état du produit. main peut porter la version courante, une branche de feature préparer un essai, une branche de release stabiliser une livraison. Le choix appartient à l’équipe et au dépôt ; l’outil de déploiement doit le rendre explicite.

La vue présente les références disponibles pour le dépôt lié au service. L’utilisateur choisit celle qu’il veut livrer. Bige Ops résout ensuite le commit correspondant afin de relier l’intention humaine — le nom de branche — à un état précis du code.

Cette distinction devient importante après une fusion. Une branche peut disparaître alors que son commit et l’image construite restent valides. L’historique doit donc conserver les deux : la référence choisie pour comprendre la décision, le commit pour identifier ce qui a réellement été préparé.

Le service garde son périmètre

Une stack réunit souvent plusieurs services : application web, worker, API ou tâche planifiée. Ils peuvent partager le même dépôt sans devoir être redéployés ensemble à chaque changement.

Bige Ops regroupe les services liés au dépôt sélectionné et laisse choisir ceux qui participent à l’opération. Une image commune peut ainsi mettre à jour app et worker, tandis qu’un service indépendant reste intact. L’interface garde le dépôt, la branche et les cibles dans la même lecture.

La découverte part aussi de la configuration de la stack. Un service déclaré reste visible même si l’inventaire live ne le remonte pas encore correctement. L’absence d’une observation cloud ne doit pas effacer silencieusement une cible configurée ; elle doit apparaître comme une information à vérifier.

L’image relie code et exécution

Le déploiement ne se résume pas à un git pull. Le code devient une image, puis cette image devient le processus exécuté sur la cible. Bige Ops prend en charge deux chemins selon la configuration du service.

Le build peut avoir lieu sur la VM. Le dépôt et son contexte sont alors transmis à la machine, Docker construit l’image, puis le service est relancé avec sa configuration d’exécution.

Le build peut aussi passer par GitHub Actions et GitHub Container Registry, ou GHCR. La CI construit et scanne l’image, la publie dans le registre, puis Bige Ops déploie le digest associé au commit demandé. Lorsqu’une image exacte existe déjà, elle peut être réutilisée. Un nouveau commit déclenche le parcours de build prévu par le dépôt.

Ces deux routes répondent à des organisations différentes. Le build sur VM reste direct et local à la cible. GHCR conserve un artefact réutilisable et portable entre les machines autorisées. L’interface présente le choix dans le contexte du service au lieu d’en faire deux produits séparés.

Les accès restent explicites

Lire un dépôt privé et lire une image privée sont deux autorisations distinctes. Une connexion GitHub peut résoudre les branches tout en recevant un refus sur GHCR si elle ne possède pas l’accès aux packages.

Le préflight de Bige Ops distingue ces situations. Il indique quand la connexion doit être renouvelée avec la lecture des packages, sans demander de coller un token dans le formulaire de déploiement. Le secret reste dans la connexion configurée ; l’opération décrit seulement le droit manquant.

Cette précision évite un diagnostic trompeur. Une erreur 403 sur le registre ne prouve ni que la branche est mauvaise, ni que l’image doit être reconstruite. Elle signifie d’abord que la cible ne peut pas lire l’artefact demandé avec les accès actuels.

L’historique garde le résultat

Une action claire mérite une trace claire. Le suivi indique les services, la référence Git et l’état de l’exécution. Les logs restent disponibles pour comprendre un échec de build, un problème d’accès au registre ou un service qui démarre mal après le déploiement.

Cette histoire ne promet pas une mise en ligne universellement instantanée. La durée dépend du build, du transfert d’image, de la VM et du démarrage de l’application. Elle promet quelque chose de plus utile : le parcours reste identifiable, du choix initial au résultat observé.

Le déploiement retrouve ainsi sa place. C’est une opération produit appuyée sur l’infrastructure, avec assez de détails pour être comprise et assez de simplicité pour être utilisée chaque jour.
